# V3.13 提案：LLM 理解表格结构、引导句、表格摘要（P2.3–P2.5）

状态：**已实施（V3.13，2026-10-21）**　｜　分支：`llm-tables`　｜　基线：`v3.12`　｜　日期：2026-10-19

## 实施结果与差异

结果见 [决策 013](../../decisions/013-llm-tables.md)、对比页 `reports/compare/v3.13-llm-tables/`。与本提案的差异：

- **整表文本**：不用 `markdown_rows_v1`，改为不经过任何结构判定的 `grid_rows_v1`（每行原样写出，合并格写 `←`、`↑`），各配置相同；表头写法只作用于检索文本。
- **表头写法**：规则与 LLM 标注的表头都写成一行列名路径（上层标签在它跨过的每一列各写一次）；依据人造表实验（`reports/experiments/v3.13-header-writing/`），由用户选定。
- **提示词 v5**：引导句与摘要不写识别文档本身的编号（摘要中单元格里的值除外）。
- **装配**：表格处理拆成表格结构、写法、表格检索文本三个环节；七种入库方式都保留在 `configs/`，`plain_text` 移入 `configs/extra/`；默认 `structured` 改为 Markdown 写法；标准对比脚本 `scripts/eval_tables.sh`。
- **计数**：表格证据指标的对照按题计变好、变差、有好有坏，另列可能变好的题数与只因单元长度变化的 token 变动（`rules/evaluation.md`）；入库成本按每张表、每次调用平均。
- **报告与入库解耦**：入库审核页从保存的中间结果生成，`report` 不需要重新入库。
- **随机扰动**：提示词改版后重新生成的文字使 1–2 题名次移动 1–2 名，LLM 各方式之间的差距不超过这一量级。


属于"检索效果优化"主题。把 roadmap 的 P2.3（LLM 处理表格文本）、P2.4（引导句）、P2.5（表格摘要）放在一个版本里做：三者都是入库时调用 LLM 处理表格。目标不是选出唯一最优，而是弄清各组合的利弊；在效果、返回 token、入库成本上都不占优的组合淘汰。

第 2 稿之后的变化：规则序列化两种写法都参与对比；LLM 不再改写表格文本，改为输出结构标注、由代码渲染；引导句与标注同一次调用；入库方式 7 种、组合 13 种。

## 已确定的问题

- **返回整表时，一律返回 `markdown_rows_v1` 写法的整表文本**，与入库方式无关。表头映射、引导句、摘要都是为了检索时的匹配；交给回答 LLM 时 Markdown 不缺信息、token 约为表头映射的一半（12 张表合计 3,951 对 8,063）。各 X-T 组合返回的文本相同，差异只来自排名。这改变了 `structured` 现有的整表文本：RL-T 的覆盖与 V3.12 相同，返回 token 下降；`RULES_VERSION` 提升，两套内置装配重建。
- **文档语言在解析阶段判定**：Docling 的解析结果没有语言字段。语言判定移到解析之后的公共步骤，写进解析结果；BM25 分析器与 LLM 表格模块都读这个字段，不再各自判定。
- **校验不通过一律退回规则序列化**（不设 `on_invalid` 开关，实验也用退回）。退回的表在报告中列出。
- **规则序列化的两种写法都保留**：2026-10-19 在当前链路下重比（512 单档，K=3），`markdown_rows_v1` 排序指标略好、表格 token 约一半，默认设置下完整覆盖少 2 题，差异与扰动同量级，不判优劣。
- **LLM 只做结构标注，表格文本由代码渲染**（理由与局限见 2.2）。
- **标注类型三类**：表头行、分节（可嵌套）、隐式合并。不设"不可拆开的行组"（信任前序解析结果）；不处理表中间重复出现的表头（续表合并已规避）；作用于全表的注释行不重复。
- **引导句与标注同一次调用**；不带引导句的入库方式复用同一输出、去掉引导句。两者各自切块：不带引导句时用满预算（与规则序列化相同）；带引导句时引导句计入每块长度，块边界可以与不带时不同（加引导句挤占正文空间是它的真实代价，计入对比）。
- **structured output**（JSON Schema 严格模式）+ **模型原生推理**；推理内容存进缓存供追溯，不校验、不入库。
- **长度**：提示词只写词数或字数，不写 token。引导句不超过 24 词（中文 48 字），代码接受的上限 64 token；摘要的词数 = 上限 token × 0.5，字数 = 上限 token × 1，上限为硬上限。
- **上下文**：表格之前的两个节点（跳过页眉、页脚，遇到表格停止，每个节点限 200 token）；提示词说明上下文只是表前文本，未必相关，由 LLM 自行判断。
- **引导句与摘要不写位置信息**（章节号、条款号、表格编号、页码），可以使用标题中的语义。
- **模型**：样例试了 3 个（见第 4 节），全量实施用 `google/gemini-3.8-flash`（2026-10-19 选定：结构标注最准确，摘要写出的标识值最利于检索）。
- 512 token 单档，不做多预算配对比较。

## 1. 组合与对比

### 1.1 入库方式 7 种 × 返回方式 2 种

| 代号 | 入库方式 | 表头由谁定 | 分节、隐式合并 | 写法 | 引导句 |
|---|---|---|---|---|---|
| RM | 规则 Markdown（`markdown_rows_v1`） | 规则判定 | 无 | Markdown | — |
| RL | 规则表头映射（`labeled_rows_v1`，现 `structured`） | 规则判定 | 无 | 列名: 值 | — |
| LM | LLM Markdown | LLM 标注 | LLM 标注 | Markdown | 无 |
| LL | LLM 表头映射 | LLM 标注 | LLM 标注 | 列名: 值 | 无 |
| LM+ | LLM Markdown + 引导句 | LLM 标注 | LLM 标注 | Markdown | 有 |
| LL+ | LLM 表头映射 + 引导句 | LLM 标注 | LLM 标注 | 列名: 值 | 有 |
| S | LLM 摘要 | — | — | 摘要 | — |

返回方式：C 命中 chunk，T 整表。去掉 S-C（摘要不对应单元格），共 13 种组合。返回方式是查询设置，同一索引用 `--table-return-unit` 切换，所以 6 种入库方式各一份索引就覆盖 12 种组合，S 一份。LM、LL、LM+、LL+ 来自同一次 LLM 调用。

### 1.2 怎么比

13 种组合全部进一张总表，在总表上读"只差一个因素"的对照，不另做实验：

| 对照 | 只差的因素 | 对数 | 主要看 |
|---|---|---:|---|
| X-C vs X-T | 返回单元 | 6 | 指标 2、3，K–覆盖–token 曲线（指标 1 在返回映射之前，两边相同） |
| RM vs RL、LM vs LL、LM+ vs LL+ | 写法 | 各 2（C、T） | 指标 1，再看 2、3 |
| LM vs RM、LL vs RL | 规则 vs LLM | 各 2 | 指标 1、2、3、入库成本 |
| LM+ vs LM、LL+ vs LL | 引导句（含它占用空间使块边界改变的影响） | 各 2 | 指标 1、2、3 |
| S-T vs 各 X-T | 摘要 | 6 | 指标 1（摘要块名次）、2、3、入库成本 |

最后按三个维度判支配：表格证据（指标 2，辅以指标 1）、返回 token（指标 3）、入库成本。三项都不优于某个其他组合的组合淘汰；剩下的组合列出各自的取舍。

判定以表格题逐题配对的名次与所需 K 为主；完整覆盖差 1–2 题不下结论（表格题约 12 道）。每种 LLM 入库方式只跑一次（模型支持时 temperature = 0，开启推理后结果仍不完全确定），报告写明。

## 2. 改什么

### 2.1 LLM 调用

每张表两次调用，提示词见 [v3.13-prompts.md](v3.13-prompts.md)：

| 调用 | 输入 | 输出（JSON Schema 严格模式） | 用于 |
|---|---|---|---|
| 结构标注 | 表格网格 + 上下文 + 语言 + 引导句词数 | 表头行、分节、隐式合并、引导句 | LM、LL、LM+、LL+ |
| 摘要 | 表格网格 + 上下文 + 语言 + 摘要词数 | 摘要 | S |

- **表格网格**：Markdown，首行列号，每行开头行号；合并单元格文字写在左上角，同行被覆盖处写 `←`，下方被覆盖处写 `↑`；空格写空。网格由解析出的表格直接生成，不经过表头判定。
- **上下文**：按阅读顺序，表格之前的两个节点，类型不限；跳过解析器标为页眉、页脚的节点；遇到表格即停止；每个节点超过 200 token 时只保留靠近表格的末尾 200 token。
- **语言**：输出用解析结果中的文档语言（见 2.11）。中文时长度按字数表述，否则按词数。
- **原生推理**：开启（样例用中档推理强度），推理 token 按输出计费，计入入库成本。
- **请求只发往支持 structured output 的服务方**，避免约束被静默忽略。

### 2.2 为什么用结构标注 + 代码渲染

LLM 直接写出表格文本（第 2 稿的 `llm_records_v1`，第 1 轮样例已试）的问题：

1. 数值写错行时查不出：校验只能确认每个数在表里出现过，确认不了它属于哪一行，错误是静默的。
2. 来源区域靠 LLM 自报引用的单元格，引用错则坐标评估错。
3. 输出量随表格大小增长，大表要分段调用，失去整表理解。
4. LLM 数不准长度，仍要代码切块。
5. 无法保留原表结构。

结构标注下，chunk 中的表格文字全部来自原表；LLM 标错只影响哪些行被重复，不会产生错误的数据；来源区域由代码算出。

**局限**：三类标注之外的理解无法表达（例如只适用于部分行的注释、缩写的含义、写在别处的单位）；这类表格的 chunk 效果退回规则序列化的水平。嵌套分节与隐式合并在现有 12 张表里没有实例，LLM 能否认出只在人造样表上验证（渲染规则另有单元测试）。

### 2.3 结构标注

| 字段 | 含义 | 校验 |
|---|---|---|
| `header_rows` | 表头所在的行，连续若干行；可为空 | 行号在表内；连续；其上方的行只能是分节标题行 |
| `sections` | 每节：标题行（连续若干行）、管辖的最后一行；管辖范围为第一个标题行到最后一行；各节平铺列出，不标上下级 | 标题行连续、在表内、不是表头行；最后一行不早于最后一个标题行；标题在表头之下的节，范围不含表头行；任意两节的范围要么嵌套、要么不相交；上下级由范围包含推出（范围更小、被包含的是下级） |
| `implicit_merges` | 空格实际沿用上方的值：列、起始行、结束行 | 起始格非空；其下到结束行的格都为空且不在解析出的合并单元格内 |
| `lead` | 引导句 | 不超过 64 token；其中每串数字在表格或上下文中出现过 |

标注之外的行都是数据行。不通过的项写进下一次请求重试一次。

### 2.4 渲染与分块（新实现 `llm_markdown_v1`、`llm_labeled_v1`）

LLM 的标注替代规则表头判定的结果，并补充分节与隐式合并；其余沿用规则序列化与 `structured_tokens` 的规则：

- **隐式合并**：被沿用的空格写作 `↑`，与解析出的纵向合并相同。
- **写法**：`llm_markdown_v1` 表头行按原样写多行（含 `←`、`↑`）；`llm_labeled_v1` 不写表头行，单列格前写列名，列名由标注的表头行按 `labeled_rows_v1` 的拼法得出。
- **每个 chunk 依次为**：引导句（LM+、LL+）、标题在表头之上的节标题、表头行（Markdown 写法）、该块数据行所属的其余各节及其全部上级节的标题行（每节的全部标题行，按从上级到下级的顺序）、数据行。原表中本块范围内的标题行在原位置写出，不再重复。
- **打包**：按最外层的节装入；当前块放不下下一节、而新块放得下时，开新块；一节放不下一个块时，按它的下一层节和行继续装入，最内层在行之间切开。节标题只和它引出的第一部分（放得下一个块时为整个子节，否则为子节标题与第一行）一起留在当前块，不单独落在块尾。块从纵向合并中间开始时写 `↑ 原值`（沿用规则）；单行超限按规则在行内切分。
- **预算**：每块（含 `passage: ` 前缀）不超过 `max_tokens`；带引导句时，引导句及其后的换行计入长度。表头与节标题计入预算；标注校验时按引导句的接受上限 64 token 留出空间，检查表头与节标题合计是否放得下每个数据行，放不下视为校验不通过。
- **来源登记**：重复的表头行、节标题、`↑ 原值` 登记为重复上下文，来源指向原单元格，计入该块的来源区域（与规则相同）；引导句没有来源区域。
- **整表文本**（返回整表时用）：所有入库方式都存 `markdown_rows_v1` 写法（规则表头判定），不含引导句。入库时表格文本化一步除了按配置的写法生成用于分块的文本，另生成一份 `markdown_rows_v1` 整表文本，一起存进中间结果；整表库 `tables.sqlite` 的 `text` 列存这一份（表结构不变）。写法相同时只生成一次。查询时不重新渲染。

### 2.5 表格摘要（配置 `[table_summary]`）

- 每张表格不再生成表格 chunk，改为一个摘要 chunk（类型 `table_summary`），来源区域为整张表；整表库存 `markdown_rows_v1` 写法的整表文本。
- 摘要不切分，超过上限即校验不通过；摘要中每串数字须在表格或上下文中出现过。
- 配置了 `[table_summary]` 时，`table_return_unit` 不能是 `"chunk"`（`--table-return-unit chunk` 同样报错）。

### 2.6 校验不通过

重试后仍不通过时，实验与实际使用都退回规则序列化：

| 标注不通过 | 只有引导句不通过 | 摘要不通过 |
|---|---|---|
| 该表改用同写法的规则序列化（LM、LM+ → `markdown_rows_v1`；LL、LL+ → `labeled_rows_v1`） | 该表不加引导句 | 该表改为 `markdown_rows_v1` 的表格 chunk |

退回的表记为"降级完成"，原因写进中间结果；入库审核页、`status` 与对比页列出降级的表。LLM 调用出错（网络、限流、无密钥）不退回，入库失败，与"被规则拒绝"区分。

### 2.7 LLM 结果的存放

- 每次调用的原始输出（含推理内容、用量、花费）作为事实存入中间结果；入库审核页的表格页显示引导句或摘要、校验与重试，以及结构标注是否正确：按页面坐标找到 `eval/table-structure/` 中该表的正确答案，相同为正确，不同时逐条列出错在哪里；网格中标出表头行、节标题行与隐式合并。标注未通过校验时只写"已退回规则序列化"，不判规则表头的对错（规则路线默认表头判定正确）。
- 按"模型 + 提示词版本 + 推理强度 + 输入内容 + 长度设置"的哈希缓存在 `.rag/llm-cache/`，`ingest --force` 复用，结果可复现；temperature = 0（gpt-6-luna 的所有服务方都不接受 temperature，此时不传）。四种 LLM 写法共用同一条缓存。
- 模型、提示词版本、推理强度、引导句与摘要的长度设置、上下文规则进入构建指纹。入库用的 LLM 与问答的 `[llm]` 分开配置，不受 `OPENROUTER_MODEL` 影响。

### 2.9 评估：新增指标

**表格 excerpt**：词坐标落在解析器给出的表格框内的 excerpt，只依赖 PDF，各组合共用。含表格 excerpt 的证据组为**表格证据组**，含表格证据组的题为**表格题**（约 12 题，实施时按坐标确认）。

| 指标 | 定义 | 依赖 |
|---|---|---|
| 指标 1 表格 chunk 名次 | 每个表格证据组：检索范围内全量 chunk 排名中（返回单元映射之前），覆盖该组表格 excerpt 中任一词的 chunk 里最靠前者的名次；S 为摘要 chunk 的名次 | 入库方式 |
| 指标 2 表格证据所需 K | 每个表格证据组：只看各方案中的表格 excerpt，在全量返回单元排名中全部覆盖所需的最少前几个单元，取各方案的最小值；每题取其表格证据组的最大值 | 入库方式 + 返回方式 |
| 指标 3 表格证据所需 token | 每题：全量返回单元排名中前"指标 2"个单元的 token 之和 | 同上 |
| 所需单元下限 | 每题：从每个证据组的可接受组合中各选一个，并集的最少单元数，与排名无关 | 同上 |
| K–覆盖–token 曲线 | K = 1…20 时：完整覆盖题数、表格证据完整覆盖题数、24 题返回 token 之和 | 同上 |
| 入库成本 | 每个配置：LLM 花费（美元，按服务方计费，含重试与推理）、LLM 调用耗时、重试次数、降级表数 | 入库方式 |

指标 1 只看"最容易找到的一块"，必须与指标 2 一起看。常规指标（K=3 的命中、完整覆盖、证据组召回、MRR、精确率、每题返回 token）照常报，作为护栏，不作为判据。

### 2.11 文档语言在解析阶段判定

- Docling 的解析结果没有语言字段。解析器输出之后增加一个公共步骤，判定文档语言并写进解析结果；各解析器适配器不变。
- 判定规则：正文文字（不计空白、数字、标点）中中日韩字符过半为中文；否则沿用现有规则（西、英文停用词出现次数多者，相同算英文）。现有规则只看文字，对象从 chunk 改为解析节点，结果应不变，实施时逐文档核对。
- BM25 分析器改为读取解析结果中的语言，不再自行判定。中文文档的 BM25 不做分词（不在本版范围），只是不被误判为英文。
- 语言判定规则进入解析阶段的指纹。

## 3. 不改什么

- 规则序列化、表头判定、续表合并、正文与列表的分块；`structured` 的 chunk 逐字不变（整表文本改为 Markdown 写法，见"已确定的问题"）。
- 数据集 3.2.0 与 ground-truth；编码器、BM25 分析器的分词与词干规则、检索器。
- 问答的 LLM 与提示词。
- 不做多预算配对比较；不调 Top-K（曲线只用于后续权衡）。
