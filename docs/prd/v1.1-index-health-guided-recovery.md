# Minimal RAG V1.1：索引健康状态与交互式恢复

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 产品 | Minimal RAG |
| 需求版本 | V1.1 |
| 状态 | 待评审 |
| 基线版本 | V1.0 Minimal RAG |
| 运行形态 | Windows 本地终端程序 |
| 目标用户 | 单用户、RAG 初学者；未来 Sales Operations Agent 的使用者 |

本需求是对 V1.0 的增量规格，不替代 V1.0 基线需求。若本文件与 V1.0 对同一行为的规定冲突，以本文件为准。

## 2. 背景与问题

V1 已具备 Manifest、Chroma 和源 PDF 的严格一致性检查，但当前 CLI 偏向技术诊断：

- `documents` 输出包含文件 Hash 等技术字段，用户难以直接判断是否可用；
- 全局配置不一致时，单个文档可能仍显示 `current`，容易误以为可检索；
- 用户必须自行理解 `ingest`、`--force`、`--prune` 的差异；
- `search`、`ask`、`chat`、`eval` 在索引不可用时直接终止，无法帮助用户恢复后继续原任务；
- “索引记录不一致”和“PDF 无法解析”共用 `invalid`，无法区分自动修复与人工处理。

V1.1 将 CLI 从“报出问题”升级为“解释问题、引导修复、修复后继续完成用户目标”。

## 3. 目标与非目标

### 3.1 目标

1. `documents` 检查当前 `documents/` 目录与索引的状态，并以用户友好的方式展示。
2. 明确区分：索引可用、索引不可用、需要人工处理。
3. 在交互终端中，经用户确认后执行合适的索引修复动作。
4. `search`、`ask`、`chat`、`eval` 在索引未就绪时引导修复；修复成功后继续原始任务。
5. 保持严格检索边界：任何不健康索引不得用于检索或生成回答。

### 3.2 非目标

- 不执行 OCR，也不自动修复损坏或扫描型 PDF。
- 不删除 `documents/` 内的源 PDF。
- 不在管道、CI 或脚本等非交互环境中等待用户输入。
- 本迭代不提供无人值守的 `--auto-repair`。
- 不引入后台任务、定时索引或 Web UI。

## 4. 状态模型

### 4.1 DocumentState

保留现有状态，并新增两个状态：

```python
NEW = "new"
CURRENT = "current"
CHANGED = "changed"
MISSING = "missing"
INVALID = "invalid"
UNPROCESSABLE = "unprocessable"
UNASSESSED = "unassessed"
```

| 状态 | 定义 | 后续动作 |
| --- | --- | --- |
| `new` | PDF 存在，但 Manifest 中没有记录。 | 普通增量索引可修复。 |
| `changed` | PDF 与 Manifest 均存在，但文件 Hash 不同。 | 普通增量索引可修复。 |
| `current` | PDF、Manifest 与 Chroma 文档记录一致。 | 无需操作。 |
| `invalid` | PDF Hash 未变，但 Chroma 的 chunk 数量或 chunk metadata 与 Manifest 不一致。 | 普通增量索引可修复；持续失败时建议全量重建。 |
| `missing` | Manifest 有记录，但当前 `documents/` 未发现对应 PDF。 | 用户决定恢复源文件或清理遗留索引。 |
| `unprocessable` | `new` 或 `changed` PDF 的只读解析失败，或无法提取文字。 | 必须人工处理源文件。 |
| `unassessed` | 因全局阻断性问题，未执行逐文档索引一致性检查。 | 先处理全局问题。 |

### 4.2 面向用户的索引状态

`DocumentState` 是底层诊断状态；默认终端表格显示以下用户状态：

| DocumentState | 用户状态 | 状态说明 |
| --- | --- | --- |
| `current` | 可用 | `-` |
| `new` | 不可用 | 新文档，尚未建立索引。 |
| `changed` | 不可用 | 文档内容已变化，原索引已失效。 |
| `invalid` | 不可用 | 索引数据与文档记录不一致，需要重新建立索引。 |
| `missing` | 不可用 | 未在 `documents/` 找到源文件，原索引不可继续使用。 |
| `unprocessable` | 需人工处理 | 无法提取文本，无法建立索引。请提供带文字层的 PDF，或先完成 OCR。 |
| `unassessed` | 不可用 | 全局索引前置条件不满足，未执行逐文档检查。 |

## 5. 健康检查策略

### 5.1 `validate_index()` 的职责

`validate_index()` 继续是健康检查的唯一核心入口，负责构造：

```python
IndexHealth(
    usable: bool,
    document_statuses: tuple[DocumentStatus, ...],
    issues: tuple[IndexIssue, ...],
)
```

它负责检查 Manifest、全局配置、Collection、每份文档、Collection 总计数和未知 Chroma 文档。

### 5.2 阻断性提前返回

下列情况使得逐文档 Chroma 一致性检查不再有实际意义。函数必须创建对应 `IndexIssue` 与 `unassessed` 文档状态后直接返回不可用的 `IndexHealth`。

1. Manifest 不存在：当前目录发现的 PDF 保持 `new`；若 Chroma 仍有记录，额外报告 `orphan_collection`。
2. 全局配置不一致：Embedding 模型、Collection 名称或任一 chunking 配置与 Manifest 不一致。所有已发现文档与 Manifest 记录均标为 `unassessed`，建议全量重建。
3. Collection 不存在：Manifest 存在但目标 Collection 不可读或不存在。所有相关文档标为 `unassessed`，建议执行普通索引。

对于 `new`、`changed`、`invalid`、`missing`、Collection 总数不一致和未知 Chroma 文档，必须继续完整检查并收集所有问题。

## 6. `documents` 命令

### 6.1 基本行为

`uv run python -m rag documents` 必须：

1. 扫描 `documents/` 下所有 PDF；
2. 执行健康检查；
3. 对 `new` 和 `changed` 文档执行只读 PDF 预解析；
4. 预解析失败时显示为 `unprocessable`，并附带原因；
5. 不在用户确认前修改 Chroma、Manifest 或源 PDF。

### 6.2 输出格式

先输出整体状态：

```text
知识库索引状态：可用
```

或：

```text
知识库索引状态：不可用
原因：发现 2 项需要处理的问题。
```

随后输出表格：

```text
文档名称 | 索引状态 | 索引状态说明 | 页数 | Chunks | 索引时间
```

- 文档名称使用相对 `documents/` 的路径；
- 默认不显示文件 Hash；
- 未知的页数、Chunks 或索引时间显示 `-`；
- 文档按相对路径稳定排序；
- 解析失败原因在对应行后以缩进行展示。

### 6.3 修复后的刷新

任何交互修复成功后，`documents` 必须重新运行健康检查并重新输出整体状态和完整表格。

## 7. 修复动作概览

### 7.1 交互前提

只有标准输入和输出均为交互式终端时，CLI 才能显示确认提示。非交互模式必须输出问题、建议命令和非零退出码，且不得修改索引。

### 7.2 修复动作与授权边界

#### 增量修复

适用：`new`、`changed`、`invalid`。

经用户确认后，CLI 在当前进程内调用普通增量索引流程；不得启动另一个 `uv run python -m rag ingest` 子进程。精确确认文案、默认值和取消行为以第 8.3 节为准。

#### 清理缺失文档

适用：`missing`。

确认源文件已永久删除后，内部执行 `prune=True` 的索引流程。精确确认文案、默认值和取消行为以第 8.3 节为准。

普通 `ingest` 不得默认 prune。`--prune` 保留为高级用户、脚本和明确授权场景的参数。

#### 全量重建

适用：`global_config_mismatch`、`orphan_collection`、`unknown_documents`。

确认后，内部执行全量 force 重建。精确确认文案、默认值和取消行为以第 8.3 节为准。

#### 人工处理

适用：`unprocessable`。

不得为该类文档显示“立即建立索引”的确认提示；具体用户说明以第 8.3 节为准。

## 8. 执行状态机与命令续跑

适用命令：`search`、`ask`、`chat`、`eval`（包括 `eval --live`）。

所有命令在执行实际检索前必须走 CLI 级“索引就绪引导”：

```text
检查索引健康状态
→ 不可用时解释问题并请求修复确认
→ 执行修复
→ 重新检查
→ 索引就绪后继续原始用户任务
```

具体结果：

| 命令 | 修复成功后的继续动作 |
| --- | --- |
| `search QUESTION` | 自动执行原始检索问题。 |
| `ask QUESTION` | 自动回答原始问题。 |
| `chat` | 进入问答循环。 |
| `eval` | 执行原始评估模式。 |
| `documents` | 重新展示状态表。 |

`Retriever.search()` 必须继续保持严格行为：当 `IndexHealth.usable` 为 `False` 时，抛出 `IndexNotReadyError`，不得直接检索。交互恢复协调仅属于 CLI 层。

### 8.1 统一的 CLI 预检与恢复状态机

`search`、`ask`、`chat`、`eval` 在创建 Embedder、调用 Chroma 查询或调用 LLM 前，必须执行同一套 CLI 预检流程。该流程的输入是“原始命令及其参数”，输出只能是以下三种结果：

```text
READY       索引已就绪，继续原始命令。
STOPPED     用户拒绝、取消或存在不能自动修复的问题；不执行原始命令。
FAILED      修复动作失败；输出失败原因，不执行原始命令。
```

流程如下：

```text
解析 CLI 参数
→ 校验本地配置与命令参数
→ 检查 documents/ 是否可扫描
→ 执行完整的 CLI 级索引预检（含 new/changed PDF 的可解析性预检）
→ 索引健康？
   ├─ 是：继续原始命令
   └─ 否：按第 8.2 节的优先级引导修复
            → 每次修复后重新预检
            → READY / STOPPED / FAILED
```

`documents` 使用同一预检与修复决策，但它的原始任务是展示状态表，因此修复后只重新展示状态，不进入检索。

### 8.2 索引阻断目录与处理顺序

当存在多个问题时，CLI 必须按下面顺序处理；每完成一个会修改索引的操作后都必须重新预检，不能基于旧的 `IndexHealth` 继续判断。

| 优先级 | 阻断条件 | 用户说明 | 可执行动作 | 用户拒绝或失败后的结果 |
| --- | --- | --- | --- | --- |
| 1 | Manifest 缺失且 Collection 有记录（`orphan_collection`） | 索引记录缺少对应的索引清单，无法验证其来源和配置。 | 全量重建；确认提示默认 `N`。 | 停止原始命令。 |
| 1 | 全局配置不一致（`global_config_mismatch`） | 当前 Embedding 模型、Collection 或分块配置与现有索引不一致。 | 全量重建；确认提示默认 `N`。 | 停止原始命令。 |
| 1 | Collection 中存在 Manifest 未记录的文档（`unknown_documents`） | Collection 含有来源不明的索引记录。 | 全量重建；确认提示默认 `N`。 | 停止原始命令。 |
| 2 | Manifest 存在但 Collection 缺失（`collection_missing`） | 索引数据不存在，需要按当前目录中的文档重新建立。 | 普通增量索引；确认提示默认 `Y`。 | 停止原始命令。 |
| 3 | `new`、`changed` 或 `invalid` | 存在可自动建立或修复的文档索引。 | 普通增量索引；确认提示默认 `Y`。 | 停止原始命令。 |
| 4 | `missing` | 已索引文档的源 PDF 未找到。 | 仅在用户确认永久删除后执行 prune；默认 `N`。 | 停止原始命令，并说明可恢复源文件后重试。 |
| 5 | `unprocessable` | 文档无法提取文本，无法建立索引。 | 无自动动作。 | 停止原始命令，列出人工处理要求。 |
| 6 | Collection 总记录数不一致（`collection_count_mismatch`） | Collection 总 chunk 数与 Manifest 总数不一致。 | 全量重建；确认提示默认 `N`。 | 停止原始命令。 |

如果一次普通增量索引修复后仍有 `missing`，CLI 必须继续展示缺失文档的确认提示；不得将“其余文档已建立索引”视为整个知识库已就绪。

### 8.3 精确交互规范

#### 8.3.1 全量重建确认

```text
索引当前不可用：<逐条问题说明>

需要全量重建全部可读取 PDF 的索引。
该操作将替换当前 Collection；源 PDF 不会被修改或删除。

是否立即全量重建？[y/N]
```

- 仅输入 `y` 或 `Y` 执行；空输入、`n`、`N` 均表示取消；
- `EOF`、`KeyboardInterrupt` 视为取消；
- 全量预构建有任一 PDF 失败时，不替换旧 Collection；输出失败文件和原因；
- 全量重建成功后必须重新预检；仅重新预检通过时才继续原始命令。

#### 8.3.2 普通增量索引确认

```text
发现以下文档的索引不可用：
- <文件>：<说明>

是否立即建立或更新索引？[Y/n]
```

- 空输入、`y`、`Y` 执行；`n`、`N` 取消；
- 索引过程继续处理其他可处理文档；
- 如任何文档处理失败，必须输出逐文件结果并重新预检；只要索引仍不可用，就不继续原始命令；
- `unprocessable` 文档不得包含在本确认列表中。

#### 8.3.3 缺失文档清理确认

```text
以下已索引文档的源文件未在 documents/ 中找到：
- <文件>

如果文件只是暂时移走，请恢复文件后重试。
如果文件已被永久删除，可清理其遗留索引；此操作不会删除源 PDF。

确认清理这些遗留索引吗？[y/N]
```

- 仅输入 `y` 或 `Y` 执行；
- 确认后执行 prune；只删除相应 `document_id` 的 Chroma chunks 与 Manifest 条目；
- 用户拒绝时不删除任何索引记录，原始命令停止；
- prune 成功后重新预检。

#### 8.3.4 无法处理文档

```text
以下文档需要人工处理，当前无法建立索引：
- <文件>：<PDF 解析失败原因>

请替换为带文字层的 PDF，或完成 OCR 后放回 documents/，再重试。
```

- 不显示确认提示；
- 不调用 Indexer；
- 原始 `search`、`ask`、`chat`、`eval` 命令停止；
- `documents` 仅展示状态表和人工说明。

### 8.4 各命令的恢复后续行为

| 命令 | 用户确认并修复成功后 | 用户取消、修复失败或需人工处理后 |
| --- | --- | --- |
| `search QUESTION` | 使用原始 `QUESTION`、`--top-k`、`--document` 执行一次检索。 | 不查询 Chroma；以非零退出码结束。 |
| `ask QUESTION` | 使用原始 `QUESTION`、`--debug` 完成一次回答。 | 不调用 LLM；以非零退出码结束。 |
| `chat` | 显示正常启动信息并进入输入循环。 | 不进入输入循环；以非零退出码结束。 |
| `eval` | 按原始模式运行检索评估。 | 不运行评估；以非零退出码结束。 |
| `eval --live` | 索引就绪且 API Key 可用后运行端到端评估。 | 不调用 LLM；以非零退出码结束。 |
| `documents` | 重新输出整体健康状态和完整文档表。 | 输出当前文档表、问题和建议；`documents` 本身可正常结束。 |

“继续原始命令”必须复用用户最初输入的全部参数，不得要求用户重新输入问题、筛选文档、`--top-k`、`--debug` 或 `--live`。

### 8.5 非索引阻断与边界

下列问题不是索引恢复流程能够安全自动解决的问题。CLI 必须说明原因与下一步，但不得提供误导性的“立即索引”确认。

| 阻断 | 影响命令 | CLI 行为 |
| --- | --- | --- |
| `.env` 配置无效，例如 `CHUNK_OVERLAP >= CHUNK_SIZE`、路径越界、`TOP_K <= 0` | 全部命令 | 显示无效配置项、当前约束和修改位置；停止。 |
| `documents/` 不存在或目录中没有 PDF | 全部需要索引的命令 | 显示期望目录路径；提示创建目录或放入 PDF；停止。 |
| Manifest 无法解析或 schema 不受支持 | 全部需要索引的命令 | 说明 Manifest 损坏/不兼容；仅在交互终端中提供全量重建确认；停止或重建后重新预检。 |
| Chroma 数据库不可读、权限不足或 I/O 异常 | 全部需要索引的命令 | 显示数据目录和底层友好错误；不得把“不可读”误判为“Collection 缺失”，也不得自动删除或重建。 |
| Embedding 模型加载或下载失败 | 索引、检索、问答、评估 | 显示模型名和网络/磁盘检查建议；不继续原始命令。 |
| `OPENROUTER_API_KEY` 缺失 | `ask`、`chat`、`eval --live` | 在索引就绪后进入第 8.6.1 节的隐藏输入与保存选择流程。 |
| OpenRouter 认证、限流或服务失败 | `ask`、`chat`、`eval --live` | 输出可读错误。`ask` 和 `eval --live` 结束；`chat` 保持会话，允许用户继续提问或退出。 |
| 空问题、无效 `--top-k`、不存在/不唯一的 `--document` | `search`、`ask` 等 | 显示具体参数错误和该子命令帮助；不进入索引恢复。 |

“Manifest 无法解析”进入全量重建前，必须明确说明旧索引将被替换。若当前目录没有任何可读取 PDF，不得提供会清空现有 Collection 的自动重建动作。

### 8.6 交互式配置与环境恢复

本节适用于所有 CLI 命令的非索引前置条件。CLI 只能交互写入 `OPENROUTER_API_KEY`；不得交互修改 `CHUNK_SIZE`、`CHUNK_OVERLAP`、`EMBEDDING_MODEL`、路径、Collection 名称或其他结构性配置。

#### 8.6.1 缺少 API Key

适用：`ask`、`chat`、`eval --live`。索引健康检查通过后，CLI 才检查 API Key。

```text
未配置 OPENROUTER_API_KEY。
该命令需要 OpenRouter API Key 才能调用 LLM。

请输入 OpenRouter API Key（输入将隐藏；直接回车取消）：
```

输入非空 Key 后，CLI 显示：

```text
请选择使用方式：
1. 仅本次运行使用
2. 保存到项目根目录 .env，供后续命令使用
0. 取消

请选择 [1]:
```

- Key 必须通过隐藏输入读取，不得回显、打印、记录到日志、异常、debug 输出或测试快照；
- 选项 `1`：本次运行使用刚输入的 Key，但不得写入 `.env` 或进程环境；
- 选项 `2`：仅原子更新项目根目录 `.env` 中的 `OPENROUTER_API_KEY`；保留其他 `.env` 内容；文件不存在时创建；
- 选项 `0`、空输入、EOF 或中断：停止原始命令，不调用 LLM；
- 用户输入的 Key 必须显式注入本次命令的 Settings/Client；不得依赖 `load_dotenv(..., override=False)` 自动覆盖现有环境变量；
- 配置完成后继续原始命令，并复用全部原始参数。

#### 8.6.2 API 认证失败

当 OpenRouter 明确返回认证或授权失败时，CLI 输出：

```text
OpenRouter 认证失败，当前 API Key 无效或没有访问权限。
是否重新输入 API Key？[y/N]
```

- 用户确认后进入第 8.6.1 的隐藏输入和保存选择流程；
- 用户拒绝时，`ask` 和 `eval --live` 结束；`chat` 保持会话并返回输入提示符；
- 不显示、比较或回显旧 Key。

#### 8.6.3 LLM 模型配置

缺少或无效的 `OPENROUTER_MODEL` 不进入交互编辑流程。CLI 必须显示当前配置项、项目根目录 `.env` 路径和正确示例，然后停止原始命令。

### 8.7 资源、目录、输入与服务恢复

本节的覆盖范围为 `documents`、`chunks`、`search`、`ask`、`chat`、`eval`。`ingest` 本身是索引修复动作，不进入“修复后重试原始任务”的协调流程。

#### 8.7.1 `documents/` 目录不存在或为空

目录不存在时，CLI 输出：

```text
知识库目录不存在：<绝对路径>
是否立即创建该目录？[y/N]
```

- 用户确认后，仅创建已验证位于项目根目录内的 `documents/` 路径；
- 创建后必须说明目录仍为空，并提示用户放入带文字层的 PDF；
- 不执行索引、检索、问答或评估；原始命令停止；
- 目录已存在但没有 PDF 时，不显示创建确认，只显示放入 PDF 的说明并停止。

#### 8.7.2 配置和参数错误

以下情况不得进入交互式重输或自动修复：

- `.env` 结构性配置无效，例如 `CHUNK_OVERLAP >= CHUNK_SIZE`、`TOP_K <= 0`、路径越界；
- 空问题；
- 无效 `--top-k`；
- 不存在或不唯一的 `--document`；
- 不合法的命令组合。

CLI 必须显示具体错误、约束及对应子命令的 `--help` 用法，然后停止。不得擅自修改用户参数或结构性 `.env` 配置。

#### 8.7.3 Embedding 模型资源失败

首次加载模型允许正常下载。若加载、下载、网络访问或磁盘写入失败，CLI 输出模型名和失败原因，并显示：

```text
无法加载 Embedding 模型：<模型名>。
请检查网络、磁盘空间和模型缓存后重试。
是否立即重试？[y/N]
```

- 仅在用户明确输入 `y` 或 `Y` 后重试同一个操作；
- 不自动等待、循环重试、切换模型或修改模型配置；
- 用户拒绝、EOF 或重试仍失败时，停止原始命令；
- `documents` 不加载 Embedding 模型，因此不触发本流程。

#### 8.7.4 Chroma 与 Manifest 基础设施错误

- Manifest 损坏、无法解析或 schema 不受支持：说明问题；仅当当前目录存在至少一份可读取 PDF 时，提供全量重建确认。全量重建前必须说明旧索引将被替换。
- Chroma 数据库不可读、权限不足或发生 I/O 错误：显示数据目录与友好错误；不得将“不可读”误判为“Collection 缺失”，不得自动删除或重建。
- `chunks` 指定的文档无已索引 chunks：显示文档名并引导用户执行 `documents` 或普通 `ingest`；不返回空白成功结果。

#### 8.7.5 LLM 服务失败与重试

适用：`ask`、`chat`、`eval --live`。

- 对超时、限流、临时网络或服务端错误，CLI 显示可读错误并提供 `是否重试？[y/N]`；每次重试都必须由用户明确确认；
- `ask`：确认后使用相同问题、检索结果和参数重新调用一次；拒绝或仍失败后结束；
- `chat`：确认后重试当前轮；拒绝或仍失败时保留 chat 会话，返回下一轮输入提示符；
- `eval --live`：确认后从头重新运行整个评估，不得只重跑部分题目并混合两次运行的结果；
- 不自动更换 LLM 模型、Provider 或重试次数。

#### 8.7.6 正常业务结果，不进入恢复流程

以下情况不是运行阻断，不得显示修复向导：

- `search` 未检索到结果：输出“未找到相关内容”；
- `ask` 或 `chat` 没有足够证据：按 Prompt 规则拒答并说明未找到依据；
- `eval` 或 `eval --live` 存在 FAIL：输出评估结果，命令按既有评估语义结束；
- 用户在 chat 中输入空行：保持会话并等待下一次输入。

### 8.8 退出码

- 用户取消修复、索引仍未就绪、需人工处理：返回索引未就绪的非零退出码；
- 配置、输入、目录或向量库基础设施错误：沿用对应错误类型的非零退出码；
- `documents` 仅展示问题且未执行用户拒绝的修复时，可返回 0；
- 所有修复完成且原始命令成功时返回 0；原始命令自身失败时保留其原有退出码。

## 9. 错误与取消

1. 用户拒绝修复或输入无效选择时，不执行写操作；输出未完成原因和建议命令。
2. 修复失败时，输出失败原因；不得伪造“索引已就绪”。
3. 修复后健康检查仍不可用时，继续展示剩余问题与下一步建议。
4. 对 `ask`、`chat`、`eval --live`，索引修复完成后仍需按现有规则检查 API Key。
5. 调试输出不得显示 API Key、Authorization Header 或业务文件全文。

## 10. 架构约束

1. `validate_index()` 负责诊断，不执行索引写入或用户交互。
2. `Indexer` 负责索引新增、更新、清理和全量重建。
3. CLI 负责展示、确认、修复协调和恢复原始命令。
4. `Retriever` 负责严格检索保护，不承担交互或修复职责。
5. 修复流程直接调用应用服务；不得以子进程方式递归调用 CLI。

## 11. 验收标准

- [ ] `documents` 显示整体索引可用性及问题原因。
- [ ] 默认文档表使用“文档名称、索引状态、索引状态说明、页数、Chunks、索引时间”。
- [ ] 默认输出不显示文件 Hash。
- [ ] `unprocessable` 与 `invalid` 可明确区分。
- [ ] 全局配置不一致或 Collection 缺失时，文档显示 `unassessed`，不显示误导性的 `current`。
- [ ] 交互式终端可确认并完成增量索引、prune 和全量重建。
- [ ] 未确认时不得执行任何写操作。
- [ ] `missing` 不会被普通 `ingest` 自动清理。
- [ ] `search`、`ask`、`chat`、`eval` 修复成功后继续原始用户任务。
- [ ] 非交互模式不会等待输入，也不会执行自动修复。
- [ ] 缺少 API Key 时可使用隐藏输入；用户可选择仅本次使用或仅更新 `.env` 中的 `OPENROUTER_API_KEY`。
- [ ] API 认证失败可在用户确认后重新录入 Key，且不会回显任何 Key。
- [ ] 目录不存在时仅在用户确认后创建；目录为空时不会误触发索引或检索。
- [ ] Embedding 模型与 LLM 的临时服务失败只在用户确认后重试，且不自动切换模型或 Provider。
- [ ] 配置错误、参数错误、Chroma 不可读等情况不会被误判为可自动索引修复的问题。
- [ ] 全部新增行为都有自动化测试，现有检索一致性保护不被削弱。
