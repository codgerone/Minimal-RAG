# 012 命中表格片段即返回整表

日期：2026-10-16　状态：已采用（V3.12）

## 背景

长表格被切成多块后，合并单元格的语义只在整表中才能看懂：全宽的分组标题（PO 25-19 数量表的"ITEM 4 … MODEL HXE34K-S1"）只出现在一块里，它所管的数据行在其他块中没有型号；确定性规则无法判定这类合并格管的是上方还是下方的行（roadmap C2）。roadmap 定了两条互相替代的路线：规则序列化 + 命中即返回整表（P2.2），或由 LLM 序列化、只返回命中的 chunk（P2.3）。本决策是第一条路线。

## 选项与决定

| 问题 | 选项 | 决定 |
|---|---|---|
| 同一张表的多块都被检索到 | 各占一个位置，或整表只占一个位置 | 只占一个位置，名次取成员中最靠前的一块，不把成员分数相加（相加会让大表占便宜）；空出的位置由后面的结果依次补上 |
| 整表文本从哪里来 | A. 查询时把各块拼起来；B. 入库时存好整表序列化结果 | **B**。各块带有重复的表头、纵向合并格补回的值、定位说明，拼接要在查询端重新推导分块器的决定；整表文本在表格文本化阶段本来就有，表头只出现一次，续表已合并 |
| 存在哪里 | Chroma，或单独的整表库 | 单独的 SQLite 整表库，与向量库、倒排索引并列，由同一 manifest 管理。整表不参与排名，只按 chunk 查表；放进 Chroma 要么得给它真向量（那是表格摘要的路线 P2.5），要么得给占位向量并在每次查询中排除 |
| 在哪一步折叠 | 检索器内部，或检索之后单独一步 | 检索之后单独一步（返回单元）。检索器只负责给 chunk 排序；混合检索在 RRF 融合之后再折叠 |
| 开关 | 构建配置，或查询配置 | 查询配置 `[retriever] table_return_unit`，不进指纹：同一索引上可直接对比，chunk 不变时单次评估即可下结论 |
| 整表大小上限 | 设上限、超过时退回只返回命中块，或不设 | 不设。本库最大的表约 5000 token；超长表格作为已知限制 |
| 评估怎么判定 | — | 整表视为返回了它的全部 chunk，坐标判定与 ground-truth 不变；指标按返回单元计，另报每题返回 token 与逐证据组所需 K |

## 结果

- structured 混合检索 K=3：完整覆盖 17/24 → 20/24，命中 20 → 22，证据组召回 75.7% → 86.1%；变好的是 PO-25-19-Q001、Q002、Q003，没有题变差。纯向量完整覆盖 16 → 19。
- PO-25-19-Q001、Q003 的表格证据组所需 K 由 12–14 降到 1–3；V3.11 变差的 Q002 恢复完整覆盖。
- K=3 下完整覆盖的上限由 22/24 升到 24/24：一张整表只算一个结果。
- chunk 与 V3.11 逐字节相同；`table_return_unit = "chunk"` 时评估结果与 V3.11 逐题相同。plain_text 没有表格，结果不变。

## 代价

- 每题返回 token（全部题之和 / 24）由 1149 增到 1860，最多一题 5627。
- 按 token 对齐时，总分上的收益与多返回几块相近：不返回整表、K=6 时完整覆盖同为 20/24（每题 1939 token），但多覆盖的是 CONTRACT-105-Q001、Q007 和 PO-25-19-Q002，PO-25-19-Q001、Q003 仍找不全。返回整表把 token 集中花在需要表格的题上。
- 只有被切成多块的表格受影响；本库只有 2 张（PO 25-19 数量表 12 块、合同的一张表 2 块）。

对比页：`reports/compare/v3.12-whole-table/`（混合检索，按 K 分页）、`reports/compare/v3.12-whole-table-semantic/`（纯向量）。
