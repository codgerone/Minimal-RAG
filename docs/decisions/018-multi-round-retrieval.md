# 018 多轮检索：两路查询、兜底一次用完、LLM 调用上限 3

日期：2026-11-03　状态：草稿（待用户确认）

## 背景

V3.14 的查询侧措施（分解、改写、HyDE、step-back 等）作为预先、一次性的处理，收益有限或被合并抵消（决策 015）。V3.15 改为多轮：第一轮用去编码原句检索，之后由 LLM 读已检索到的材料，判断哪些问题已可回答、为还不能回答的问题派生子问题或兜底检索，LLM 只用于查漏补缺（提案 v3.15）。

## 方案

- **两路查询**：纯检索（原问题检索一次）与多轮检索都保留，由查询设置 `[query] mode` 选择（`retrieval` / `multi_round`），内置配置默认 `retrieval`；`ask`、`chat`、`eval` 按它走，`--query-mode` 临时覆盖。不进指纹。
- **兜底一次用完（安排 A）**：一个问题第 2 次检索时，往下取、改写、HyDE、step-back 同时检索，Q0 另加补上翻译；各方式各返回 K 个此前未交给 LLM 的单元，方式之间不合并。第 2 次之后不再检索该问题，它仍可派生子问题。分两次兜底（安排 B）不采用。
- **LLM 调用上限默认 3**（含作答调用），`[multi_round] max_llm_calls` 可配置。

## 实验结果

RM-T（structured，返回整表），安排 A，K = 3，规划模型 google/gemini-3.8-flash，提示词 multi_round_v3 / multi_round_answer_v3；数据集 3.4.1，32 道可回答题 + 2 道无答案题，第 0–3 次生成。按上限 5 运行一次，上限 2–4 从同一次运行截取（`reports/multi_round/a-v3/`）。数值为 4 次生成的平均。

| 4 | 30.75 | 25 / 26 | 78.75 | 7.75 / 2.25 | 7.5 / 6.0 | 22.3 秒 | $0.0139 |

- 完整覆盖：交给 LLM 的单元（展示序列）凑齐全部信息项的题数。单轮同 token：单轮排名中累计 token 不超过多轮展示序列 token 的前若干单元。变好 / 变差：凑齐向量的支配关系（`rules/evaluation.md`"查询侧的比较"），多轮在展示序列上计算、未凑齐排在最后，单轮在全量排名上计算。
- 136 次运行中 90 次第一次调用即作答，平均调用 1.4 次。上限 4、5 相对 3 多出的是 CONTRACT-105-Q003（交货地点在第 3 轮才凑齐）。上限 2 只有第一轮的 3 个单元，明显变差。
- 收益主要来自派生问题：每次生成派生问题第 1 次检索凑齐 10–13 个信息项，兜底各方式合计 0–7 个。兜底只在 5 题中出现，各方式之间分不出高下。
- 相对去编码 + 译文按支配关系接近持平（上限 3 净值 +0.75）：PO-24-12-Q002、Q003、Q005 等题单轮译文把证据排到第 1，多轮第一轮不带译文排到第 2；同 token 下多轮完整覆盖多 4 题。
- 判断：可回答题已接受的证据完整覆盖与交给 LLM 的材料相同（证据被拒 0）；误判可回答 1 题（CONTRACT-105-Q010，4 次生成都出现：答案需用签约日期把"签约后 N 天"换算成日期，LLM 未派生问题）。无答案题 E001-602-Q003 判为可回答，答案说明发票未记载，PO-25-19-Q008 未回答。

## 结论

- 多轮检索作为第二路查询保留，默认仍为纯检索：多轮每题约 22 秒、$0.014，适合要求完整性的提问。
- 兜底采用安排 A；上限默认 3：上限 4、5 只多 1 题，耗时与花费几乎相同，留作配置。
- 兜底各方式的取舍待数据：兜底在本数据集上很少触发，保留全部方式；出现更多需要兜底的题后再评估。
- 已知问题：需要换算的问题 LLM 可能直接按材料原文作答而不派生依据（CONTRACT-105-Q010），留待提示词或端到端问答评估处理。
