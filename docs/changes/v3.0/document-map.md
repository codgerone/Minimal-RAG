# V3.0 文档地图与权威边界草案

状态：文档地图已用于 V3.0 需求和架构编写。返回 [审核入口](README.md)；依据 [总体方案](system-design.md) 与 [规则对应表](capability-inventory.md)。本页规划权威边界；下文仍以代码形式标出的未创建路径是计划路径，不是假链接。

## 1. 草案与现行规格如何分开

结构通过审核后，先在 `docs/changes/v3.0/spec/` 编写完整草案：`requirements.md`、`architecture.md` 及其 `requirements/`、`architecture/` 子目录。草案入口声明状态、阅读顺序和每份文档权威内容，内部建立双向链接。

当前 `docs/requirements.md`、`docs/architecture.md` 和 `docs/README.md` 继续代表已实现系统。本审核包由其自己的 README 导航，不将未批准的新规格混入现行入口。V3.0 实现与验收完成时，再保存现行规格的历史快照、检查旧链接并一次性切换入口；具体发布清单在实施前补齐。

草案必须独立完整：现行文档是迁写来源，不能让 V3.0 规格靠“其余同 V2.0”才能解释行为。审核包中的方案和盘点随后作为设计记录保留，正式字段与规则的权威迁入规格后，审核包不得继续承担第二份权威。

## 2. 总需求目录（R0）

计划文件：`spec/requirements.md`。读者：用户、需求评审、架构和测试人员。权威内容：系统目标、范围、主链阶段摘要、跨阶段行为及系统级验收。

1. 目标、业务价值、非目标、运行前提。
2. 系统输入输出与源文档身份。
3. 能力选择与装配规则：接口角色、可用插件能力、预设、默认配置和交互式配置入口。
4. 入库主链：发现与预检 → 解析组装 → 分块 → 必需产物 → 编码 → 发布。每阶段说明输入、目的、核心行为、输出、失败及子需求入口。
5. 读取与查询主链：健康门、浏览、检索、证据问答及独立聊天轮次。
6. 正式检索评估主链与人工审核；live 冒烟范围。
7. 配置变化、状态、增量更新、恢复和操作作用域等跨阶段规则。
8. 系统级错误、安全与交互约束。
9. 功能等价、阶段对照、故障和效果验收；已知限制。

主文档在每个大接口阶段列出本轮可用实现及能力摘要，不只放插件名称或“详见子文档”。不展开 SDK 选项映射或 Python 模型代码。

| --- | --- | --- |

| R-processing `document-processing.md` | 主解析与补充内容如何形成完整文档？纯文本与版面行为、内容保留、阅读顺序、组装及原生回退；不复制表格评分公式 | 解析组装；解析和文档语义实现人员 |
| R-tables `table-selection.md` | 如何提取候选并选定结构？四工具九策略、结构恢复行为、准入、分组、评分及失败/同分规则 | 表格分支；规则实现与测试人员 |
| R-header `table-header.md` | 如何认定表头？完整判定步骤、类型词法、阈值、原因及限制 | 最终表格内容准备；领域规则人员 |

| R-chunking `chunking.md` | 文档如何生成等价 chunks？字符规则、普通文本/List 正文、token 分块、表格切分与重复上下文、来源和终止 | 分块；分块及 tokenizer 测试人员 |

| R-operations `operations.md` | 命令怎样检查状态、交互、失败和恢复？全部命令矩阵、健康状态、动作、凭据/debug/退出码 | 跨阶段运行操作；CLI 与恢复人员 |
| R-evaluation `retrieval-evaluation.md` | 怎样建立标准证据、计算指标、发布报告和比较配置？完整评估及审核规则 | 独立评估主链；用户、评估及测试人员 |

来源发现、Embedding、当前单路检索、单轮问答各自规则尚不足以需要单独需求文件，保留在总需求相应阶段。插件多不意味着按工具拆出多份需求。

现行表格文本化中的“超限切分”归 R-chunking，文本化语法及带来源行结构仍归 R-table-text；winner 页面展示归 R-artifacts。迁写时移动完整规则并互链，不同时在三处保留算法。指标公式仅 R-evaluation 完整定义，架构引用而不另写公式版本。

## 4. 总架构目录（A0）

计划文件：`spec/architecture.md`。读者：开发、架构和评审人员。权威内容：边界、模块协作、数据流、依赖方向、公共模型定位、全局约束及代码组织总览。

1. 系统边界、外部依赖与唯一运行实现。
2. 装配、入库、查询回答、评估及恢复的端到端数据流。
3. 顶层接口目录：职责、输入输出语义、消费者、持久化、失败影响及内部组成。
4. 公共模型在链中的位置：原始事实、中间判断、完整结果、持久化和展示。
5. 接口连接、插件注册、按需实例化和生命周期。
6. 配置、索引身份与兼容性；只链接完整指纹算法。
7. 发布生效点、健康检查和错误传播的系统级约束。
8. 代码分层与依赖方向；插件和 SDK 的边界。
9. 各阶段架构子契约导航及技术验证门。

总架构必须使读者看清大接口的输入输出模型及内部接口组合；模型表解释职责并链接字段权威位置。复杂字段在子契约完整定义，主文档不复制一个“简化但不同”的类定义。

| A-assembly `assembly-contracts.md` | 接口/插槽/插件/绑定模型；一份连接关系；接入条件、能力匹配与静态校验；插件配置引用与生命周期；组合、规则身份及 fingerprint 生成算法 | 装配和接口框架人员；不复制各领域模型或各工具完整参数 |

| A-artifacts `processing-artifacts.md` | 产物构建、审核 renderer、envelope、暂存结果、诊断引用及渲染输入；失败阶段 | 审核与产物人员；文件发布事务属于 A-storage |
| A-storage `storage-publication.md` | Store 端口、统一 metadata codec、Manifest/快照/journal/发布结果完整模型；写入顺序、生效、回滚、prune、路径与隔离 | 索引与恢复人员；不复制公共 Chunk/来源字段定义 |

## 6. 容易重复的概念如何分配

| 概念 | 完整权威位置 | 其他文档如何使用 |
| --- | --- | --- |
| 接入行为 | R-assembly；可执行模型在 A-assembly | 总文档阶段摘要；领域接口只声明引用规则及具体条件 |
| 文档/节点/chunk ID 与来源 | A-data | 工具映射给出转换过程，发布只引用，不重写公式 |
| 表格决策状态与字段 | A-tables；触发规则在对应需求 | Assembler 消费决策，不自行重判 |
| 表格正文 / 表格切分 | R-table-text / R-chunking | 相互链接，正文语法与切分动作各定义一次 |
| 构建 fingerprint | A-assembly | Manifest、运行和评估持有值与快照，调用同一算法 |
| 业务健康状态 / 技术模型 | R-operations / A-runtime | Indexer 使用明确请求，持久化不写派生健康状态 |
| 发布与恢复字段、路径 | A-storage | A-runtime 引用结果与操作，不复制日志模型 |
| 审核内容 / 产物结构 | R-artifacts / A-artifacts | A-storage 只规定何时发布和怎样回滚 |
| 检索评估指标 / 数据字段 | R-evaluation / A-evaluation | summary 只派生，不另做指标或阈值 |

需求与架构分别回答行为和技术表达，允许互相引用；同一层面不得出现两套字段、枚举或公式。SDK 使用的事实转换与领域规则必须分清，不以工具行为自动决定业务政策。

## 7. 编写与审核顺序

1. 本总体设计和地图审核，关闭需要用户裁决的冲突原则。
2. 编写完整总需求阶段摘要与子需求，将能力盘点展开成逐规则对应，核对正常、边界和失败验收；不新增功能。
3. 审阅需求一致性，再完成总架构及完整子契约，包括字段、可空条件、枚举、依赖和迁移方式。
4. 检查公共模型对既有正文、ID、来源、Prompt、存储事务的影响，完成必要技术验证；不以旧测试通过替代新契约验证。
5. 检查链接、标题锚点、代码围栏、重复权威、旧规则引用、参数和失败状态闭合，形成编码就绪清单，交用户最终审核。

步骤 2 的需求规格和步骤 3 的[总架构](spec/architecture.md)及九份子契约已获用户审核，[规格级编码就绪复审](spec/architecture-review.md)通过。[技术验证](spec/technical-validation.md)已完成编码前第三方机制实测；真实 V3 等价门与评估独立性仍须在实现后验证。
