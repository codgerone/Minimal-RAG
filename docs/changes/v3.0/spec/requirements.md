## 1. 目标、范围与前置条件

本系统面向 Windows 本地终端、Python 3.11、单用户、多份数字型 PDF，发现 `documents/` 内文档，构建本地索引，提供增量入库、浏览、语义检索、证据问答、聊天及正式检索效果评估。用户可通过配置选择符合接口契约的插件组合，比较不同配置的结果。V3.0 只有一套接口、插件和编排运行实现；已产出的 V2.0 索引、审核产物和评估报告作为只读历史证据保留。

输入包括原始 PDF、有效装配配置、构建/查询参数及评估数据集；输出包括解析结果、chunks、向量记录、manifest、必要审核产物、检索命中、回答与正式评估报告。前置条件是文件处于允许目录、源身份可确定、插件组合合法；调用外部 LLM 的命令还需有效 API Key。

本轮不增加 OCR 扫描件支持、图片理解、自动跨表续表拼接、LLM 表格文本生成、元数据自动过滤、关键词或混合检索、多轮聊天记忆、Agent/工具调用、Web UI、阶段缓存恢复、热替换或通用流程编辑器。未验证的旋转、CropBox/MediaBox 不一致页面不扩大支持承诺。

## 2. 能力选择与装配

接口、插件、装配三种定义分离。系统启动执行命令前，检查每个接口的必接/选接/条件接入、one/multi 数量、连接闭合、输入输出及能力匹配；通过后本次运行固定配置。无条件选接接口缺席与接入后运行失败、成功零结果不可混淆。连接按真实数据依赖形成串接或并接；并接不承诺物理并发。非法装配必须在加载模型、读取业务 PDF 或修改存储前失败并说明原因。

本轮交付复现既有能力的纯文本与结构化两份预设。纯文本预设使用 PyMuPDF 按页解析、无表格提取、字符分块；结构化预设使用 Docling 版面、四工具九策略表格处理、表头与文本化、结构化 token 分块。两者都按实际执行阶段生成必需可审计快照，并使用 E5、Chroma、确定性语义检索、证据问答、健康检查、恢复和评估，且存储和操作作用域相互隔离。两个内置预设固定命名为 `plain_text`、`structured`；自定义配置在向导通过校验后由用户命名，名称与构建身份分离。默认选择指向已保存的最佳装配，V3.0 初始指向 `structured`；`--config NAME` 可直接选择已保存配置，`--configure` 进入交互式选择或创建引导。V3.0 不提供旧版运行模式或旧 `--pipeline` 参数。`ingest --all-configs` 对所有已保存、已校验且可入库的配置分别建索引。完整装配行为见[能力装配需求](requirements/assembly.md)，命令与无索引引导见[运行操作需求](requirements/operations.md)。

## 3. 文档发现与身份

DocumentRegistry 默认扫描项目根 `documents/` 及子目录内 `.pdf`，扩展名大小写不敏感；忽略隐藏或临时文件。选择器只接受相对路径或唯一文件名，不接收越界路径；同名不同相对路径须按完整路径区分，文件名不唯一时必须报歧义。相对路径相对 `documents/`，使用 `/`；大小写不敏感路径冲突须拒绝。文档 ID 沿用实际已发布的 `sha256(relative_path.casefold())` 前 16 位十六进制，文件内容另计算完整 SHA-256 file hash。完整 ID 规则和碰撞校验由架构定义，不能因旧文档曾写“全文 hash”而改变既有稳定身份。

不存在、空目录、目录路径错误、PDF 损坏、可打开但无可用文本/结构是不同事实，分别报告。Registry 只生成源文档身份事实，不把索引健康结论写入原始事实。详情及命令表现见[运行操作需求](requirements/operations.md)。

## 4. 文档解析与组装

DocumentProcessor 对同一源 PDF 产生完整语义文档与处理证据。必接主解析器和组装器；表格提取是 multi 选接分支，接入后表格选优器条件必接。主解析和提取都以源 PDF 为输入，二者可并接；选优需主解析的 slot/原生结构、候选和 PDF 原文字词证据，组装器需主文档及最终采用内容，因而分别在依赖完成后串接。组装器没有补充结果时保留主解析正文、顺序和来源。

纯文本主解析按页读取、无 OCR；结构化主解析保留 Docling 阅读顺序、文本、列表、原生表格和 provenance，排除图片元素但保留独立图注。Docling 整文失败不自动切换纯文本；可选提取工具某页失败记录事实并继续其他成功页。表格每个原生占位最终恰有一个表格节点：可评分组采用 winner，其余采用原生回退，不重复或伪造来源。确定最终结构后做[表头判定](requirements/table-header.md)和[表格文本化](requirements/table-text.md)；正常 `undetermined` 按行列兜底，不写成异常。下游只消费组装完成的语义结果，具体规则见[文档处理需求](requirements/document-processing.md)和[表格需求](requirements/table-selection.md)。

主解析整体失败、组装证据缺失或完整性检查失败时，本次文档不进入分块，已有 active 构建保留。现有规则未定义 Docling 部分页失败可发布的情形，本轮不新增该状态。

## 5. 文档分块

Chunker 将完整语义文档转换为非空、有序、可追溯的 chunk 集合。内置纯文本配置按当前已发布 V2 构建保持每页独立、Python 字符长度上限 300、重叠目标 50 的递归字符分块；其他合法配置可选择自己的字符参数。结构化配置按文档阅读顺序组合普通文本，List 和表格独立分块，并按实际 E5 passage tokenizer 的 512-token 硬上限切分，必要时重复上下文但不丢原文。各分隔顺序、正文语法、overlap、超限退化、稳定 ID、来源及终止规则由[分块需求](requirements/chunking.md)完整定义。

每个 chunk 的正文既用于 embedding，也作为检索后提供给 LLM 的证据正文；`passage: ` 仅编码时加入。空结果、超限、缺失原文覆盖、重复 ID、来源不一致或无法继续消耗输入时不得交付可发布 chunk 集合。纯文本与结构化的既有正文、边界、顺序、来源及稳定 ID 分别保持等价；统一模型不能改变这些结果。

## 6. 处理产物与审核

每份成功入库的 PDF 在发布前必须保存与实际装配相符的逐阶段可审计快照：主解析原生事实与公共结果、已接入的表格提取/选优/内容准备结果、完整组装文档和最终 chunks。表格提取、选优、内容准备及分块有人工审核 HTML；表格页面按 slot 分区，分块页面按顺序逐块展示，不再单独生成 winner HTML。审核页不重算业务判断；任何适用的必需文件失败均阻止该 PDF 发布并保留旧 active。快照不作为检索输入，诊断开关不改变检索数据。详情见[产物需求](requirements/processing-artifacts.md)。

## 7. 向量化与索引发布

Embedder 对 passage/query 使用同一锁定 E5 模型身份与不同的既有前缀，编码并归一化，验证数量、维度与有限值，显式交付向量存储；模型同维不代表兼容。Indexer 按目标组合的文件 hash、构建配置、向量与必需产物决定跳过或重建。单文档新 payload 完成且可校验之后，发布协调器持久化恢复证据，再改变向量和产物，最后原子保存 manifest；manifest 保存成功为生效点。失败时恢复旧 active 状态或保留可阻断查询的恢复失败证据。

全量 force 所有文档先构建完成，任何预构建失败目标索引完全不变；collection 缺失的修复不能发布部分重建；已登记 artifact invalid 不得只凭 file hash/count 跳过。这三项是已确认 D-04 限定纠偏。prune 仅在确认永久删除后对所选组合作用域执行；旧 V3 构建清理发生在提交验证后，失败保留恢复日志并阻断该索引，恢复器重试。具体阶段、保留结果和验收见[索引生命周期需求](requirements/index-lifecycle.md)。

## 8. 索引健康与查询入口

健康检查将源 PDF、manifest、collection、active 产物及恢复日志回读为可判定状态。组合级结构或配置阻断时，文档状态为 `unassessed`，不先逐份断言 current/invalid；这是 D-03 限定纠偏。单文档 `current/new/changed/missing/invalid/unprocessable` 各有独立触发条件。只读命令不自动改写索引；交互修复须按问题优先级、用户确认和所选组合作用域执行，复查后才继续原请求。出现未完成 journal 时先判定事务提交或回滚，不能 force 覆盖证据。状态和操作规则见[运行操作需求](requirements/operations.md)。

`browse`/`chunks` 读取已发布记录，按确定顺序与页来源筛选，不读取 embedding。Retriever 在索引可用后将问题编码为 query 向量，按可选的显式文档范围查询目标 collection。K 必须为正；结果返回 ID、正文、文档与全部来源页、块序号、距离和相似度。为确定同距离 K 边界，先取至少 K+1 个候选，在边界同分时扩展直到超出同分组或读完作用域，再按未舍入距离和 chunk ID 升序决胜，严格返回最多 K 条。正常零结果不是异常。现阶段只有语义检索，不新增关键词、融合或自动元数据过滤。

## 9. 证据问答与聊天

Chatbot 串接同一个 Retriever、PromptBuilder 和 LanguageModel。Prompt 只能把实际命中的 chunk 作为业务事实，要求证据不足时明确拒答，保留文档、真实页面和 chunk ID 引用；不得用配置、manifest、审核 HTML 或诊断代替证据。`ask` 一次检索和生成；chat 运行中装配固定，每轮独立检索，不保留跨轮记忆。`--debug` 只向当前终端展示实际命中及最终消息，API Key 不打印。OpenRouter API Key 仅在需要调用 LLM 时检查，认证失败仅允许一次重新输入并重试；其他服务失败不自动循环。内置装配保留 `OPENROUTER_MODEL` 运行时覆盖，不因 LLM 模型变化重建索引。详见[运行操作需求](requirements/operations.md)。

外部 LLM 的回答文字不要求跨运行逐字相同；固定输入时检索证据、引用、Prompt 消息、模型参数和调用行为必须与历史基线等价。

## 10. 正式检索评估

默认 eval 读取已审核的 PDF 独立 ground truth 与目标构建的 test set，先检查问题、组、每条 excerpt 的审核映射、可接受完整 chunk 组合、索引身份和正文来源，再逐题调用同一个 Retriever，生成逐题命中事实、可复算指标、每 PDF JSON/HTML、整体汇总与比较。检索返回 chunk 而不返回标准组；评估器按预先标注的最小可接受组合派生组命中，excerpt 审核映射不直接计分。可回答问题的相关片段前置、独立事实完整覆盖与跨文档污染分别度量，不用单个指标代表整体效果。完整状态、公式、空值、汇总和审核规则见[检索评估需求](requirements/retrieval-evaluation.md)。

完整性失败是 `invalid`，检查通过后的执行/产物失败是 `failed`，全部必需输出可回读后才是 `completed`；失败不得进入正式基线。同一配置重跑用唯一身份，不覆盖历史。这是 D-05 限定纠偏。旧 V2.0 报告不改写；V3.0 映射须在新旧 chunk 正文与来源核对后重新审核。`eval --live` 只做问答冒烟，不混入正式检索指标或默认加载 LLM。

## 11. 错误、安全、系统级验收与限制

参数、选择、主解析、表格、分块、编码、存储、发布、健康、评估和 LLM 错误必须带可判断阶段和作用域，向用户显示简洁原因与下一步，不默认泄露 traceback、文档全文、Prompt 全文、embedding 或 API Key。机器状态、原因、阶段不得用自由字符串或 message 推断。进入发布事务前的单文档失败保留旧 active build；发布中失败按事务回滚或保存恢复失败证据；正常零表、零检索结果及证据不足拒答不是系统失败。具体退出和交互见[运行操作需求](requirements/operations.md)。

端到端验收使用相同 PDF/hash、固定配置与历史基线，逐阶段对比解析与选优、表头/正文、chunk 内容/边界/顺序/来源、向量身份、检索命中顺序与正式指标；浮点比较不凭展示舍入值，容差依据具体算法契约及实际基线。LLM 比较请求构造与调用行为。应覆盖纯文本和结构化预设、所有八类命令、默认与显式选择、成功零结果、失败/降级、重建/回滚及不同组合隔离。D-03—D-05 明确按书面承诺纠偏，并单列旧实现差异测试；不能把这些失败路径混写成“完全不变”。

已知限制：历史正式数据只有五份 PDF、24 道题，不能证明未知文档泛化；图片与扫描件内容不在本轮支持范围；结构表格上游缺字、串列或坐标不可靠时，下游规则不能补造真实内容；正式检索评估不衡量 LLM 回答质量。凡现有规范尚无真实依据的异常情形，不预设新状态或发布策略。
