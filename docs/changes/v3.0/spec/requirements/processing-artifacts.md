# 文档处理产物与审核视图需求

状态：**V3.0 需求已审核通过；逐阶段快照增补已完成一致性复审。** 本文件完整定义[总需求第 6 节](../requirements.md#6-处理产物与审核)的可审计快照要求；文件契约见[处理产物架构](../architecture/processing-artifacts.md)，发布顺序与回滚见[索引生命周期需求](index-lifecycle.md)。

## 1. 目标与共同规则

每份成功入库的 V3.0 PDF 必须有与该次向量及 manifest 同时生效的完整可审计快照，供人工沿处理链核对解析、表格处理、组装和分块结果。两份内置装配及后续合法自定义装配采用**同一阶段规则**，不按预设名称或特定解析路径规定两套文件包。快照是结果与证据，不是检索、选优、组装或分块的数据源；审核页不得重新运行业务判断。

关键接口被实际执行时，必须保存其真实输出；未接入的条件接口不生成该接口文件，且快照目录清单须说明未接入。接口已接入但本 PDF 结果为零时，须保存明确的空结果与对应审核页，不得把“零结果”伪装为“未接入”。同一阶段成果只保存一次：DocumentAssembler 的完整文档结果代表 DocumentComposer、DocumentAssembler 和 DocumentProcessor 交付的这一阶段，不为后两者再复制文件。主解析器原生结果虽然不是公共接口输出，仍须保存，便于区分第三方解析与公共模型转换的问题。

## 2. 必需阶段成果

| 阶段 | 每次实际执行后的必需内容 | 人工审核重点 |
| --- | --- | --- |
| 主解析器原生结果 | PyMuPDF 或 Docling 本次解析得到的、可回溯到原 PDF 的原生事实快照；不得为生成快照重新解析 PDF | 对照公共模型检查信息是否在转换时丢失 |
| MainParser | 完整 `PrimaryDocument`，含页/阅读序、节点或 slot、来源和警告 | 主解析器实际交付给下游的内容 |
| TableExtractor（已接入时） | 所有已接插件的 `TableExtractionReport` **汇总一份**，保留插件身份、绑定顺序、全部候选和逐工具/逐策略失败证据；原始候选不伪造 slot 归属 | 单个 HTML 借用下游已保存的匹配证据按 slot 清晰分区；每个 slot 内按工具/策略展示相关候选，未归属候选单列，零候选明示 |
| TableSelector（已接入时） | 完整准入、分组、评分、选优、原生回退及原因证据，不仅是 winner 最小摘要 | 单个 HTML 内按同一 slot 顺序清晰分区，逐 slot 展示候选去留、分组、分数和最终采用/未采用原因 |
| TableContentPreparation（已接入时） | 表头判断与文本序列化结果**合存一份**，按 slot 关联被采用表格；零表格也有真实空结果 | HTML 按 slot 展示采用结构的可读表格、表头状态及原因、完整序列化文本；不把它标为最终 chunk |
| DocumentAssembler | 完整 `ParsedDocument`；不为 DocumentComposer、DocumentProcessor 重复输出 | 主解析与表格结果合成后的阅读顺序及来源 |
| Chunker | 实际交付给编码器的完整 `ChunkBatch`，正文、顺序、ID 和来源与入库记录一致 | HTML 顶部显示文档、构建和分块公共信息；每个 chunk 独立成框并按最终顺序展示完整正文、页码、来源、类型及重复上下文标记 |

四个 HTML（提取、选优、内容准备、分块）仅展示人工需要着重核查的事实；JSON 保留完整细节。提取 JSON 只保存 TableExtractor 的原始输出；提取 HTML 在 Selector 完成后使用其不可变匹配证据作**展示分组**，不得反向改写提取报告、重新执行匹配或把展示归组当成提取器输出。被多个 slot 评估的候选可在相关分区以同一 candidate ID 重复展示，并明确标记最终归属；没有任何可归属 slot 的候选放入“未归属候选”分区，不得丢弃。提取与选优页面均以稳定 slot ID、主解析顺序和明显视觉边界组织，同一 slot 的零候选、拒绝或回退也要可见，不得把不同 slot 的候选平铺混排。可读表格须按真实物理 cell 与合并关系绘制；仅在表头确认为 `identified` 时标示表头区域。原文 HTML 转义、不截断关键正文，不展示 embedding 浮点数组或无助人工判断的完整坐标清单。序列化文本与最终 chunk 文本在不同阶段展示：完整表格恰落在一个 chunk 时可以相同；分块、重复表头/合并格上下文或定位前缀可能使最终 chunk 不同。原有独立 `winner-review.html` 不再生成，其审核信息由内容准备与分块页面承接。

## 3. 发布、失败与验收

全部适用的 JSON、HTML、原生证据及快照文件清单先进入本次事务私有暂存区。清单须列明实际生成的文件、身份、大小与校验摘要及未接入阶段；发布前逐文件回读，核对同一 document/build/fingerprint、slot/候选/节点引用和 `ChunkBatch` 与待写向量记录的正文及来源。任一适用文件缺失、损坏、渲染失败、跨文件不一致或路径越界，均使本次 PDF 构建失败，旧 active manifest、向量和快照保持不变。成功发布后仅 active manifest 引用的完整快照有效；孤儿目录不能自动变成 active。V2.0 已有产物只读保留，不回填或改写。

验收覆盖两份内置装配及合法自定义装配、多个 slot 和同 slot 多工具候选、零候选/零 winner/零表格、原生回退、表头未确定、合并单元格、长表拆块及重复上下文、纯文本空白页、HTML 特殊字符、文件及身份错配、审核页失败和全量 force 中途失败。逐阶段 JSON 要能区分“原生解析 → 公共主解析 → 提取/选优 → 内容准备 → 完整组装 → 最终分块”的问题位置；任何成功案例均不得依赖审核产物反向产生业务结果。
