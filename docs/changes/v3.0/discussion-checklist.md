## 已确认决策

### 01 — 等价性与验收边界（用户已确认）

固定输入与配置下，关键阶段结果和业务行为等价：

- 解析文本、阅读顺序、表格选择、表头判定、文本化及来源语义一致。
- chunk 正文、边界、顺序、重叠和来源一致，不能只比较数量。
- 固定基线下检索命中内容、顺序、同分决胜和正式评估指标一致；浮点容差依据现有契约及基线确定，不在此任意指定。
- LLM 的检索上下文、Prompt、消息构造、模型参数和调用行为一致，不要求外部服务重复生成逐字相同的回答。
- 相同失败条件下，阻断、继续、降级、恢复及影响范围一致。
- 时间戳和每次运行身份按生成规则、关联关系与不变量验证，不要求不同运行的值相同。
- 验证采用关键阶段结果对照与端到端验收，不能仅凭总体检索指标判定等价。
- 内部表示允许调整，但不得改变原有业务语义；发现实现与现行规格冲突时单独讨论，不把行为修正混入重构。

旧数据格式、稳定 ID 及使用方式兼容政策见第 02 项。

### 02 — 独立重建与唯一运行实现（用户已确认）

- 保留 V2.0 既有索引、manifest、解析与分块产物、审核视图和正式评估报告作为历史基线，V3.0 使用独立存储，从原 PDF 重新构建，不覆盖旧基线。
- V3.0 不要求直接读取旧持久化格式，也不要求一次性转换旧索引；允许根据统一接口契约重新设计 JSON、向量 metadata 和 manifest。
- 保留既有文档 ID 和两条基线的 chunk ID 生成规则；新旧存储隔离。
- 命令选择方式已被后续用户决定替代：V3.0 删除旧 `--pipeline v1|v2` 参数，保留原命令及其他既有参数语义；默认指向最佳装配，支持交互式配置选择/创建，并允许直接指定已保存配置。先前“旧参数兼容映射”的讨论结论不再适用。
- 重构完成后只有 V3.0 运行实现；不存在系统版本切换、旧 V2.0 运行分支，或通过保留整套旧运行实现来包装成插件的兼容模式。
- 全部解析、分块、索引、检索、问答、健康检查、恢复与评估均进入 V3.0 的接口、插件和编排体系。既有算法及已确认规则的保留不等于保留旧系统运行模式。
- V2.0 历史产物不作为 V3.0 正常运行的数据来源；基线验证可以只读历史证据进行比较。
- 保留原标准答案及证据标注；验证新旧 chunk 正文及来源一致后建立 V3.0 对应 test set，保留审核和溯源记录。旧 test set 绑定系统、pipeline、collection 和构建指纹，不能只因 chunk ID 相同就直接视为 V3.0 test set；旧报告不改写。

### 03 — 已确认的设计方法与局部选择

用户同意配置选择插件、启动时装配与校验、提供复现既有能力的预设组合。接口、插件和装配的具体字段模型尚待助手完成设计及审核。

用户明确要求接口定义与插件定义分离：大模块应清楚描述内部小接口及串接、并接、选接、必接规则；接口中插件相关内容仅表达可接插件的约束，插件具体定义和配置使用独立数据模型。前一轮混合 processor/plugin/options 的示例没有获准作为配置模型。

- 用户已确认连接关系只维护一份权威定义，反方向自动推导；完整通用方法见 AGENTS.md，不在本清单复制定义。
- 用户已确认文档处理中的组装器必接。无补充解析结果时保留主解析内容、顺序和来源语义；不再为此反复征求选择。
- 用户明确要求从局部案例提炼方法，应用到整个系统；不要求用户逐个接口或模块参与设计。
- 此前助手提出的具体 YAML、模型名及组合结构不是已批准契约。主解析、表格提取、选优的案例用于推导实际依赖，不据此提前引入图片解析等新功能。
