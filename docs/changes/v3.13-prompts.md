# V3.13 提示词（第 4 稿）

两次调用：**结构标注**（含引导句）与**摘要**。每份分 system 与 user 两部分，`{...}` 为代码填入的内容。实际使用英文原文；每份原文后附中文译文与说明，请在本文件中审。

第 4 稿的改动：摘要第 4 条补充"只用来排序的序号本身不足以指向一行"与"逐个列出，不用范围代替"；其余同第 3 稿。

第 3 稿的改动：LLM 不再改写表格文本，改为输出结构标注（表头行、分节、隐式合并）与引导句，由代码渲染；输出用 JSON Schema 严格模式约束；开启模型原生推理；长度只写词数或字数；上下文改为表前两个节点，并说明它可能与表格无关；引导句与摘要不写位置信息。

## 0. 共用部分

### 0.1 表格网格的读法（写在每份 system 的末尾）

英文原文：

```
How to read the table grid:
- The first line gives column numbers (c0, c1, ...). Each following line is one grid row and
  starts with its row number (r0, r1, ...).
- A merged cell's text is written in its top-left position. Positions it covers in the same row
  are written "←"; positions it covers in rows below are written "↑". Treat them as one cell.
- An empty position is an empty cell. "\|" is a literal "|" inside a cell.
- No header has been marked; decide from the content which rows are headers.
```

中文译文：

```
表格网格的读法：
- 第一行给出列号（c0、c1……）。之后每一行是网格的一行，以行号（r0、r1……）开头。
- 合并单元格的文字写在它的左上角位置。它在同一行覆盖的位置写"←"，在下方各行覆盖的位置写"↑"。把它们当作同一个单元格。
- 空的位置就是空单元格。"\|"是单元格内的字面竖线。
- 表头没有被标出；请根据内容判断哪些行是表头。
```

### 0.2 user 部分

英文原文：

```
Document language: {language}

<context>
The text that comes just before the table in the document, nearest last. It may describe the
table, or it may be unrelated to it; judge for yourself. It is given to help you understand the
table. Your answer does not have to draw on it, and where it does, you need not keep its
wording.
[{节点类型}] {较远的节点}
[{节点类型}] {紧挨表格的节点}
</context>

<table>
| row | c0 | c1 | c2 | ... |
| r0 | COMPANY | ITEM | DESCRIPTION | ... |
| r1 | ↑ | ↑ | ↑ | ... |

</table>
```

中文译文：

```
文档语言：{language}

<context>
文档中紧挨在表格之前的文字，离表格最近的在最后。它可能是对表格的说明，也可能与表格无关，请自行判断。提供它是为了帮助你理解表格。你的回答不必用到它；用到时也不必保留它的原话。
[{节点类型}] {较远的节点}
[{节点类型}] {紧挨表格的节点}
</context>

<table>
（表格网格）
</table>
```

说明：
- 上下文最多两个节点，跳过页眉、页脚，遇到表格停止，每个节点最多 200 token；没有节点时写 `(none)`。
- `{节点类型}` 是解析器给出的类型（title、paragraph、list 等），帮助 LLM 区分标题与正文。
- `{language}` 取解析结果中的文档语言（Spanish、English、Chinese）。提示词用英文写，避免把输出带成中文；输出语言由这一行与规则决定。

### 0.3 重试（校验不通过时追加在对话末尾）

英文原文：

```
Your answer did not pass these checks:
- {未通过的项，每项一行}
Return a corrected answer in the same format.
```

中文译文：

```
你的回答没有通过以下检查：
- {未通过的项，每项一行}
请按同样的格式返回修正后的回答。
```

说明：
- 未通过的项来自代码校验：LLM 返回后，代码按提案 2.3 节的校验规则逐条检查（摘要按 2.5 节），每条不通过的规则生成一行英文，写明字段、序号、行列号和原因，原样填入这里。LLM 不参与生成这些信息。
- 检查项与对应的反馈：
  - 表头行：行号超出表格范围；不连续；上方有非节标题的行。
  - 分节：标题行不连续、超出范围或与表头行重叠；last_row 早于标题行或超出范围；标题在表头之下的节包含表头行；两节范围交叉（既不嵌套也不相交）。
  - 隐式合并：列号或行号超出范围；first_row 的格子为空；下方的格子不为空、写着"↑"或属于解析出的合并单元格。
  - 引导句、摘要：超过长度上限；含有表格和上下文中都没有出现过的数字串。
- 反馈示例：`sections[2]: last_row 40 is outside the table (rows 0-35)`；`sections[1] and sections[3] overlap without one containing the other (rows 5-12 and 9-20)`；`lead: 39 words, the limit is 24 words`。
- 长度超限时只给词数或字数，不给 token 数：代码按 token 判定（引导句上限 64 token），反馈时换算成词数（英、西）或字数（中文）。

## 1. 结构标注（含引导句）

### system

英文原文：

```
You analyze the structure of a table extracted from a PDF. The table will be split into
retrieval chunks of consecutive rows, and each chunk will be searched and read on its own.
Code builds every chunk from the original cells; you do not rewrite any text. Your annotation
decides what each chunk repeats, so that a reader who sees only one chunk still understands it.

Annotate:
1. header_rows: the rows that hold column labels. They must be consecutive. They are repeated
   at the top of every chunk. Leave the list empty if the table has no such rows.
2. sections: a section is a group of rows introduced by a title. The title takes one row or
   several consecutive rows. Give the title rows as title_rows and the last row of the group as
   last_row. The title is repeated in every chunk that contains any row of the group. Sections
   may be nested. List every section as its own item, parents and sub-sections alike; do not
   put one inside another. A sub-section's rows, from its first title row to its last_row, lie
   entirely within its parent's rows; code works out the nesting from these ranges. A title
   above the header rows that applies to the whole table is a section that runs to the last
   row.
   Decide by meaning, not by layout: a row spanning the full width may be a title, a total or
   a note. Rows that total or summarize other rows, and notes, are not section titles.
3. implicit_merges: empty cells that, by meaning, repeat the value above them in the same
   column (the table writes a value once and leaves the following rows blank). Give the column,
   first_row (the row that holds the value) and last_row (the last row that repeats it). Mark
   only cells that are empty in the grid, not cells written "↑", and not cells that are empty
   because there is no value.
4. lead: one sentence in the document language, at most {lead_limit}, that tells a reader what
   the table is about: what it lists, what a row stands for and what the columns give. You may
   use the meaning of headings in the context. Do not mention where the table is in the
   document (section, clause, article or table numbers, page numbers). Describe the table in
   general terms; do not copy values from its cells. Do not state anything that the table or
   the context does not support.

Every row not named in header_rows or in any title_rows is a data row and is kept as it is.
Give row and column numbers as integers (r12 is 12, c3 is 3).

{表格网格的读法}
```

中文译文：

```
你要分析一张从 PDF 中提取出来的表格的结构。这张表会被切成若干个由连续行组成的检索块，每一块都会被单独检索、单独阅读。每一块都由代码用原始单元格拼成；你不改写任何文字。你的标注决定每一块要重复哪些内容，使只看到其中一块的读者也能看懂它。

请标注：
1. header_rows：放列名的行。它们必须是连续的。它们会在每一块的顶部重复。表格没有这样的行时，列表留空。
2. sections：节是由一个标题引出的一组行。标题占一行，或连续的若干行。把标题所在的行写作 title_rows，把这一组的最后一行写作 last_row。只要某一块含有这一组中的任意一行，这一块就会重复这个标题。节可以嵌套。每一节（无论父节还是子节）都单独列为一项，不要把一节放在另一节里面。子节的行（从它的第一个标题行到它的 last_row）完全位于父节的行之内；嵌套关系由代码根据这些范围推出。位于表头行之上、适用于整张表的标题，是一个一直延续到最后一行的节。
   按含义判断，不按版式判断：一个横跨整行的行可能是标题、合计或注释。合计或汇总其他行的行，以及注释，都不是节标题。
3. implicit_merges：按含义来说重复其上方同列值的空单元格（表格只写一次值，后面几行留空）。给出列号、first_row（写有这个值的行）和 last_row（重复这个值的最后一行）。只标在网格中为空的单元格，不标写着"↑"的单元格，也不标因为本来就没有值而为空的单元格。
4. lead：一句话，用文档语言，不超过 {lead_limit}，告诉读者这张表是关于什么的：它列出了什么、一行代表什么、各列给出什么。你可以利用上下文中标题的含义。不要提这张表在文档中的位置（章节、条款、条文或表格的编号，页码）。用概括的说法描述表格；不要照抄单元格中的值。不要陈述表格或上下文不支持的内容。

凡是没有写进 header_rows、也没有写进任何 title_rows 的行，都是数据行，原样保留。行号和列号写成整数（r12 写作 12，c3 写作 3）。

（表格网格的读法）
```

### 输出约束（JSON Schema，严格模式）

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["header_rows", "sections", "implicit_merges", "lead"],
  "properties": {
    "header_rows": {"type": "array", "items": {"type": "integer"}},
    "sections": {"type": "array", "items": {
      "type": "object", "additionalProperties": false,
      "required": ["title_rows", "last_row"],
      "properties": {"title_rows": {"type": "array", "items": {"type": "integer"}},
                     "last_row": {"type": "integer"}}}},
    "implicit_merges": {"type": "array", "items": {
      "type": "object", "additionalProperties": false,
      "required": ["column", "first_row", "last_row"],
      "properties": {"column": {"type": "integer"}, "first_row": {"type": "integer"},
                     "last_row": {"type": "integer"}}}},
    "lead": {"type": "string"}
  }
}
```

说明：
- `{lead_limit}` 为 `24 words`，中文文档为 `48 Chinese characters`。代码按 multilingual-e5 分词器校验，接受的上限为 64 token。
- 字段顺序是有意的：引导句放在最后，在模型完成结构判断之后写。思考由原生推理承担，不设思考字段。
- 第 2 条的嵌套用平铺列表加行范围表达，不用"节里套节"的递归结构：递归 Schema 并非所有服务商的严格模式都支持；平铺时上下级由范围包含唯一确定，交叉的范围由校验拒绝。
- 第 2 条最后一句"按含义判断"针对规则做不到的事（roadmap C2）：横跨整行的行可能是标题、合计或注释，只有看懂内容才能区分。
- 第 3 条的最后一句排除"本来就没有值"的空格。例如交货计划里某批次没有交货，空格就是没有值，而不是"同上"。
- 第 4 条（引导句）与第 2 稿相比：不写位置信息；把"说出表格属于文档哪一部分"改为"说出表格是关于什么的，可以利用标题的含义"。
- 不带引导句的入库方式复用同一次输出，忽略 `lead`。

## 2. 摘要

### system

英文原文：

```
You write a retrieval summary for a table extracted from a PDF. The summary replaces the table
in the search index: a question about anything in the table should be able to find this
summary. After it is found, the full table is shown to the reader, so the summary does not need
to carry every value.

Rules:
1. Write one paragraph in the document language, at most {summary_limit}. This is a limit, not
   a target.
2. State what the table is about. You may use the meaning of headings in the context. Do not
   mention where the table is in the document (section, clause, article or table numbers, page
   numbers).
3. State how the table is organized: what a row stands for, what the columns are (with their
   original labels), and any groups, subtotals or totals.
4. Copy exactly the values that a question would use to point at a particular row or group. A
   sequence number that only orders the rows (such as 1, 2, 3 or 1.1, 1.2) does not point at a
   row by itself. If they do not all fit, say what kinds there are and give as many as fit, in
   the original order. List them one by one; do not replace a run of values with a range.
5. Do not list the other values the rows report; say only which kinds of values the table gives.
6. Do not state anything that the table or the context does not support.

{表格网格的读法}
```

中文译文：

```
你要为一张从 PDF 中提取出来的表格写一段检索摘要。在检索索引中，这段摘要代替这张表：凡是关于表中任何内容的问题，都应该能检索到这段摘要。检索到之后，读者会看到完整的表格，所以摘要不必包含每一个值。

规则：
1. 用文档语言写一段话，不超过 {summary_limit}。这是上限，不是目标。
2. 说明这张表是关于什么的。你可以利用上下文中标题的含义。不要提这张表在文档中的位置（章节、条款、条文或表格的编号，页码）。
3. 说明表格是怎么组织的：一行代表什么，各列是什么（使用原来的列名），以及有哪些分组、小计或合计。
4. 原样照抄问题会用来指向某一行或某一组的值。只用来给行排序的序号（如 1、2、3 或 1.1、1.2）本身不足以指向一行。放不下全部时，说明有哪几类，并按原来的顺序尽量多列。逐个列出，不要用范围代替一串值。
5. 不要列出各行报告的其他值；只说明表格给出了哪几类值。
6. 不要陈述表格或上下文不支持的内容。

（表格网格的读法）
```

### 输出约束（JSON Schema，严格模式）

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["summary"],
  "properties": {"summary": {"type": "string"}}
}
```

说明：
- `{summary_limit}` 为"上限 token × 0.5"个词（512 预算下约 254 words），中文文档为"上限 token × 1"个字。上限 = `max_tokens` − `passage: ` 前缀，是硬上限：超过即校验不通过、重试。
- 第 4 条（第 4 稿）：第 2 轮样例中 luna、deepseek 把编号当作唯一的标识值（交货计划只写 1.1–3.4，付款计划只写期次 1–6），gemini 在预算表把逐项列出改成了范围，因此补两句。哪一列能指向行仍由模型按内容判断，不要求写描述。
- 第 4 条区分"标识一行的值"（问题用来指向某一行的值，如名称、编号）与第 5 条的"该行报告的值"（如数量、金额、日期）。哪些列起标识作用由 LLM 按表格内容判断，不预设表格类型。
- 第 2 条与第 2 稿相比：不写位置信息。
- 摘要中出现的每串数字须在表格或上下文中出现过（代码校验）。
