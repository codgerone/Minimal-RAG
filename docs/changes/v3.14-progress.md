## 讨论中确认、需遵守的细节

- 一次检索 = 检索器排名 + 换算返回单元，返回的是返回单元的排名；之后的融合、选取、评估都以返回单元为对象，chunk 没有自己的名次。`UnitRanking.chunk_ids` 只作溯源，供 `plain` → `eval` 的 V3.13 表格证据指标使用。
- 规划成本：命中缓存的调用记缓存中当次的费用与耗时（第 4a 项已改）。
- 评估方法的讨论过程与朋友的意见：`tmp/检索优化效果怎么衡量-讨论稿.md`、`tmp/RAG检索优化评估_讨论意见与实验建议.md`（不进 git）。用户明确的要求：比较与 K 无关；不设阈值，进一名也算；信息项之间无先后、无权重；一个措施只在不引入其他因素时评估。

- 写法都由问题本身生成，可叠加，与先后无关；"改写后的译文"之类串联写法不做。
- 拆解与否都包装成同一个问题列表 `{"questions":[{"id":"Q1","text":...}]}` 交给一次写法调用；写法按编号返回。
- 编码要从改写、翻译、HyDE、step-back 全部去掉；原句保留（即问题本身）。
- 不向规划 LLM 发送文档名；文档语言、编码由代码填入提示词变量。
- 拆解不限个数。
- RRF 的 60 是常数；每条检索与融合结果都是全量排名；K 是原问题返回单元的总数。
- 对比页：只有顶部"左侧 vs 右侧"勾选（左为右的真子集，或两侧全空）；模块依次列出；K 选择放在需要的模块里；不合法时配置框标红、未评估时标黄；命中、完整覆盖写 x/总题数；成本列为每题检索次数、每题查询耗时、每题 LLM 费用。
- P5 移到 V3.15；跨文档的第二轮扩大检索范围记入 roadmap。
