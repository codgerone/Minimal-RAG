## 实施中用户确定的事项（提案未写到的部分，收尾时写入归档提案的"与提案的差异"）

1. 新增动作 `stop`：`retrieval_method_left` 为 false、`open_sub_questions` 为 0、且不再派生时，问题记为 `exhausted`。
2. 输出加 `withdrawals`：撤回状态为 pending 的问题。
3. 输入加 `scope`（检索的文档与选中它们的标识编码），提示词说明编码是用户给文档的标签、不出现在文档中。v1 抽查中 LLM 因材料不含编码而拒收正确材料，这是加它的原因。
4. 新问题用 Q0 的语言写；note 用 Q0 的语言写。v3 抽查中仍有个别 note 是西班牙文、英文，用户决定不收紧（note 只给 LLM 看）。
5. 提示词原则（用户 2026-11-03）：代码负责的事提示词不代劳（下一次检索要哪些兜底文本由代码列在 `retry_texts`，能否再检索看 `retrieval_method_left`）；LLM 必须做的事不遗漏（未接受的材料不再出现、父问题可接受子问题已接受的材料）；不写模棱两可或举例式的说法；不写与测试集或文档类型挂钩的要求（作答改为"事实按材料原样陈述，不换算、取整或补全"，单轮 `ask` 提示词 `rag/query/prompt.py` 同步修改）。
6. retry 与 derive 按用途区分（retry：要查的仍是这个问题本身，只是没检索到；derive：还需要的已是另一个问题），不加"partial 不能 retry"之类的禁令或校验；retry 的兜底文本重述整个问题。
7. 抽查页"结论先看"（版面：题号、类型、问题合为一列；终止原因与 Q0 最终状态同格；LLM 调用列写总数及规划、作答各几次；表格外加横向滚动）：结果列（已回答 / 未回答，证据是否凑齐，误判可回答标红，漏答注明证据是否交给过 LLM）、终止原因（中文：Q0 已回答 / 达到调用上限 / 没有待检索的问题）与 Q0 最终状态分列、耗时拆开（各轮检索次数与时间；各次调用的时间、输入 / 输出（其中推理）token）。评估页沿用这些写法。
