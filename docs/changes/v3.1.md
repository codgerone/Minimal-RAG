## 1. 目标与不做的事

**目标**：保留现有全部功能和两份内置装配的检索效果，把系统改造成"小而清楚、便于后续做检索实验"的地基，同时重建文档体系、产物目录和审核视图。

**保留的功能**：PDF 发现与增量入库、两种解析（PyMuPDF 按页 / Docling 版面）、四工具九策略表格提取与选优、表头判定、表格文本化、两种分块、E5 编码、Chroma 存储、语义检索、证据问答与聊天、索引状态检查、正式检索评估。

**不做**（留给下一阶段"检索效果优化"）：换 embedding 模型、混合检索、元数据过滤、查询改写、表格文本格式改动。本轮只换地基，不动会改变检索结果的算法。

**验收**：
1. 两份内置装配重建后，正式评估指标**不低于** `v3.0-codex`（plain_text 命中率 4.2%、structured 20.8%，及其余指标）。由于本轮不改算法，预期 chunk 正文与基线一致、指标相同；如有差异会逐条说明原因。
2. 所有命令可用；新的审核页通过你的验收。
3. 应用代码量显著下降（目标约为现在 1.26 万行的三分之一），每个模块一句话能说清职责。

## 3. 新架构

### 3.1 数据主链

```
入库   PDF ─→ 解析器 ─→ 文档(文本/列表/表格占位)
              │
              └→ 表格提取器×N ─→ 选优 ─→ 表头 ─→ 文本化 ─┐
                                                          ↓
                                    组装后的文档 ─→ 分块器 ─→ chunks ─→ 编码器 ─→ 向量库
                                                                   └→ 审核报告(HTML) + 中间结果(JSON)
查询   问题 ─→ 编码器 ─→ 向量库检索 ─→ 命中 ─→ Prompt ─→ LLM ─→ 回答
评估   标准证据 + 问题 ─→ 同一检索器 ─→ 自动判定命中 ─→ 指标 ─→ 评估报告
```

### 3.2 可替换环节（接口）与内置实现

只有下面这些环节有接口；其他都是普通函数或类，需要第二种实现时再抽接口。

| 接口 | 内置实现 | 为什么值得可替换 |
|---|---|---|
| 解析器 Parser | `pymupdf_pages`、`docling_layout` | 解析方式直接决定正文质量 |
| 表格提取器 TableExtractor（可接多个） | `pymupdf`、`camelot`、`docling`、`unstructured` | 多工具比较本身就是项目亮点 |
| 表格文本化 TableFormatter | `row_text_v1`（即现行格式） | 下一阶段要试验不同表格文本格式 |
| 分块器 Chunker | `characters`、`structured_tokens` | 分块是检索调优的主要变量 |
| 编码器 Embedder | `e5_small` | 下一阶段要试验更强的多语言模型 |
| 检索器 Retriever | `semantic` | 下一阶段要加混合检索、过滤 |
| LLM | `openrouter` | 可换模型或服务商 |

向量库固定为 Chroma，封装在一个类里；表格选优和表头判定目前各只有一种算法，作为普通模块存在。

### 3.3 装配配置（示例）

```toml
# configs/structured.toml
name = "structured"
description = "Docling 版面 + 四工具表格选优 + token 分块"

[parser]
use = "docling_layout"

[[table_extractors]]
use = "pymupdf"
[[table_extractors]]
use = "camelot"
[[table_extractors]]
use = "docling"
[[table_extractors]]
use = "unstructured"

[table_formatter]
use = "row_text_v1"

[chunker]
use = "structured_tokens"
max_tokens = 512
overlap_tokens = 32

[embedder]
use = "e5_small"

[retriever]
use = "semantic"
top_k = 4

[llm]
use = "openrouter"
```

启动时校验：插件名是否存在、参数是否合法、组合是否成立（例如配了表格提取器但解析器不提供表格位置时报错）。

**构建身份**：影响索引内容的配置（解析、表格、分块、编码）计算出一个指纹，记录在索引的元数据里，而**不作为目录名**。配置改了之后，`status` 会提示"索引与配置不一致，需要重建"。

### 3.4 索引的一致性策略

- 单个文档入库顺序：处理 → 写中间结果和报告 → 写向量 → **最后**更新清单 `manifest.json`（原子写入）。
- 清单是唯一的"已入库"依据。中途崩溃时，清单仍指向旧状态；`status` 发现向量库和清单不一致，就标记该文档"需重建"，下次 `ingest` 自动处理。
- 全量重建（`--force`）先在新目录建好整份索引，成功后再替换旧目录，失败则旧索引不受影响。

### 3.5 代码目录

```
rag/
  cli.py            命令入口
  config.py         读取并校验 configs/*.toml
  registry.py       插件注册表
  models.py         公共数据：SourceDoc / Document / Table / Chunk / Hit
  ingest/           sources.py、parsers/、tables/（提取器、选优、表头、文本化）、chunkers/、pipeline.py
  index/            embedder.py、store.py、builder.py、status.py
  query/            retriever.py、prompt.py、llm.py、chat.py
  eval/             dataset.py、judge.py（自动判定）、metrics.py、runner.py
  reports/          HTML 模板与各审核页渲染
configs/            plain_text.toml、structured.toml

```

## 5. 审核视图的改法

通用原则：**结论先行、问题优先、预期与实际并排、技术细节默认折叠**；所有页面共用一套样式，支持浅色/深色；从 `reports/index.html` 能一路点到任何页面。

**评估页（重点）**

```
┌ 总览 ───────────────────────────────────────────────────┐
│ structured · K=3 · 2026-10-06      命中 5/24  完整覆盖 2/24 │
│ 与上次对比：命中 +0  覆盖 +0  跨文档污染 −0.0             │
│ 按文档：E001-602 1/2 ▏ORDER 24-12 0/6 ▏…                 │
│ [只看未命中] [只看跨文档污染] [全部]                     │
└─────────────────────────────────────────────────────────┘
┌ PO-24-12-Q001  ✗ 未命中  ·  3 条结果全部来自其他文档 ─────┐
│ 问题：订单 24-12 包含哪几款产品？…                        │
│ ┌ 标准证据 ────────────┐ ┌ 实际检索 Top-3 ─────────────┐ │
│ │ ORDER 24-12 · 第1页   │ │ #1 ✗ ORDER 25-15 · 第2页     │ │
│ │ HXF300 | 10,000 | …  │ │    相似度 0.889  [展开正文]  │ │
│ │                       │ │ #2 ✗ ORDER 25-19 · 第2页 …  │ │
│ └───────────────────────┘ └──────────────────────────────┘ │
│ ▸ 判定依据与 chunk ID（折叠）                              │
└─────────────────────────────────────────────────────────┘
```

**入库审核页**
- 解析页：按页展示解析出的元素（标题/段落/列表/表格位置），每页一块，可与 PDF 页码对照。
- 表格页：每个表格位置一节，**各工具候选表并排渲染为真正的表格**，胜出者高亮，评分只显示四项总分和胜出理由，详细计算折叠；页首汇总"共 N 张表，M 张由候选胜出，K 张回退原生"。
- 分块页：顶部是分块统计（数量、长度分布、超长/过短提示），每个 chunk 一张卡片，标题行为"#3 · 表格 · 第 2 页 · 312 tokens"，正文直接展示，来源节点 ID 折叠。

## 6. 文档体系

```
docs/
  README.md      一页地图：每份文档回答什么、你是否需要读
  overview.md    系统现在能做什么、不做什么、怎么用、怎么验收      ← 你读
  design.md      数据主链、可替换环节、存储与一致性、关键取舍      ← 你读前两节
  rules/         算法细则：表格选优、表头判定、表格文本化、分块、评估指标
                 每份开头一段"规则摘要"给你看，正文供实现和面试复盘
  decisions/     一项重要决策一页（背景 / 选项 / 结论）
  changes/       每次迭代一份提案（本文件即 v3.1）                  ← 你主要审这里
  archive/       history.md：V1→V3 的演进与关键指标；旧文档原文靠 git 标签保留
```

约定：
- `overview.md`、`design.md`、`rules/` 永远描述**当前系统**，随实现更新；变化过程只在 `changes/` 和 git 历史里。
- 字段级定义、枚举和异常处理写在代码类型和测试里，不进文档。
- 过程性材料（checklist、实施日志、技术验证）不写进 `docs/`，用提交信息记录。
