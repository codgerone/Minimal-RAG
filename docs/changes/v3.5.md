# V3.5 提案：表格文本去脚手架（新增 `markdown_rows_v1`）

状态：**实施中**　｜　分支：`retrieval-opt`　｜　基线：`v3.4`　｜　日期：2026-10-08

属于"检索效果优化"主题。`row_text_v1` 给每个单元格都加上字段名，没认出表头时加 `第N行/第M列`，表格 chunk 的大部分 token 是脚手架而不是表格内容。本次新增一种 `TableFormatter` 实现，用新装配与 V3.4 基线对比。

## 1. 目标与依据

数据来自 V3.4 的 `structured` 索引和评估结果（K=3，过滤开启）：

- 24 道题中有 13 道的证据在表格 chunk 里：命中 10 道，完整覆盖 7 道。
- 表格 chunk 共 28 个，其中 16 个在 400 token 以上，接近 512 的上限。PO-25-19 交货计划表的列名展开约 30 token，每行重复 7 次，所以每个 chunk 只放得下 2 行；PO-25-19-Q001、Q003 的证据分散在 6–9 个 chunk 里，K=3 下不可能完整覆盖。
- 7 个表格 chunk 的表头没认出来，单元格前只有不携带语义的 `第M列`。

目标：在不判断表格语义的前提下，缩短表格文本、减少脚手架，让一个 chunk 装下更多行。

## 2. 改什么

### 2.1 新格式器 `markdown_rows_v1`

- **表头行**：认出表头时，表格文本的第一行是表头行，每列写多级表头路径（各级用 ` / ` 连接）；没有路径的列写空。没认出表头时没有表头行，也不写 `表头未确定。`，表格各行原样输出。
- **数据行**：一行表格对应一行文本，写作 `| 值 | 值 | … |`。
  - 空格写空，缺失的格写 `〔缺失单元格〕`。
  - 单元格内的 `|` 写作 `\|`。
- **合并单元格**：值写在左上角的位置。同一行里被覆盖的位置写 `←`，下面各行被覆盖的位置写 `↑`。
- **无法定位到网格的文字**：写在最后一行，保持原文。
- **来源记录**：每行仍然记录对应的表格行和单元格 ID，坐标判定的评估照常可用。

格式对照（25-15 批次表，表头未认出，第 1 列的 MODEL 纵向跨两行）：

```
| MODEL | 1st Delivery | 2nd Delivery | 3rd Delivery | 4th Delivery | 5th Delivery | 6th Delivery |
| ↑ | 25.09.25 | 10.10.25 | 10.12.25 | 10.03.26 | 10.05.26 | 10.07.26 |
| HXE12ESX |  | - | 20,000.00 | 20,000.00 | 20,000.00 | 20,000.00 |
```

### 2.2 分块器 `structured_tokens`：纵向合并的续接

- **表头行**：表格切成多块时，每块开头重复表头行。这一条沿用现有机制，不改。
- **从纵向合并中间开始的块**：块里第一行被这个合并单元格覆盖的位置，最左一格写作 `↑ 原值`，其余写 `←`。补出的原值登记为重复上下文，类型为合并单元格，来源指向合并单元格的左上角。块中间的被覆盖位置照常只写 `↑`。

示意（公司列的 ENSA 纵向跨 3 行，块在第 2 行之后切开）：

```
第 1 块
| COMPANY | MODEL | QTY |
| ENSA | HXE12ES | 132,180 |
| ↑ | HXE13ES | 9,910 |

第 2 块
| COMPANY | MODEL | QTY |
| ↑ ENSA | HXE33K-S1 | 5,018 |
| ELSE | HXE12ES | 2,600 |
```

合并单元格同时跨多列时，第 2 块这一行写作 `| ↑ ENSA | ← |`。

- **`row_text_v1` 的输出不变**：现有的合并说明续接逻辑保留给它。
- **单行就超限**：沿用现有的行内切分。

### 2.3 回答提示词

`rag/query/prompt.py` 的系统提示词增加一句：表格以 Markdown 行表示；单元格为 `←` 表示与左侧单元格属于同一个合并单元格，为 `↑` 表示与上方单元格属于同一个合并单元格；`↑ 值` 表示该合并单元格起始于本段之前，此处补出它的值；合并单元格的含义需根据上下文判断。查询侧设置，不触发重建。

### 2.4 装配与文档

- 新增装配 `configs/structured_markdown_table.toml`：只把 `table_formatter` 改为 `markdown_rows_v1`，其余与 `structured` 相同。
- `docs/rules/table-text.md`：增加 `markdown_rows_v1` 一节，并更新"已知限制"。
- `docs/rules/chunking.md`：写明两种格式器下的表格续接规则。
- `overview.md`：更新表格文本化的说明和基线。

## 3. 不改什么

- **表头判定**：25-19 交货日期表把第一行数据判成了表头，属于表头判定的问题。
- **跨页表格拼接**：续表丢失表头。
- **合并单元格的语义判定**：分节标题、合计等含义不做判断；横跨整行的合并行只覆盖一行，不带进后续的块。
- **检索侧的相邻 chunk 扩展**：可以缓解证据被切开的问题，但不在本次范围内。
- **`row_text_v1` 与 `plain_text` 装配**：`plain_text` 不处理表格。
- **评估规则和数据集 3.1.0。**
- **原文中的 `←`/`↑` 字符**：会与续接符号混淆；现有文档中没有出现，记入已知限制。

## 4. 怎么验收

1. **测试**：覆盖新格式器的各种情况（有/无表头、横向/纵向/双向合并、空格、缺失格、`|` 转义、无法定位文字），以及分块器的续接和来源记录；`row_text_v1` 下 `structured` 的 chunk 正文与 V3.4 逐字相同。
2. **入库**：`structured_markdown_table` 全部文档入库成功，所有 chunk 都有细粒度来源区域；用 Chrome 无头截图自查入库审核页的表格 chunk。
3. **评估**：K=3、过滤开启，与 V3.4 的 `structured` 基线并排对比，比较以下各项：
   - 命中率、完整覆盖、证据组召回、MRR、Chunk 精确率、跨文档污染、文档识别；
   - 表格 chunk 个数与 token 数；
   - 完整覆盖上限（证据最多落在 3 个 chunk 内的题数 / 24）。
4. **回答**：用 `structured_markdown_table` 对 PO-25-19-Q003 运行 `ask`，检查回答是否正确理解了跨块的 `↑`。
5. **交给你审**：评估报告和入库审核页，结论里列出逐题变化，特别是 13 道表格题。
