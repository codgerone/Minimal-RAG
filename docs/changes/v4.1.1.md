# V4.1.1 提案：按需重建（逐文档指纹、步骤结果缓存）

状态：**草稿，待审**　｜　分支：从 `main` 建 `index-rebuild`　｜　基线：V4.1（数据集 4.1.0）　｜　日期：2026-11-12

V4.2（Word）开工前先做这一版。V4.1.1 不加文档类型，数据集不变。

## 需要你拍板的问题

### 1. `--force` 要不要绕过步骤缓存

**事实**：本版加入步骤结果缓存（第 3 节）以后，缓存键里的规则版本如果漏提升，`--force` 全量重建仍然会读到旧的缓存结果，旧输出就会保留下来。现有的 OCR 缓存和 LLM 缓存已经是这样：`--force` 不重做 OCR，也不重新调用 LLM。

**选项**：
- **A（推荐）**：`--force` 仍然使用缓存。另加 `ingest --refresh-cache`，只重算解析、表格提取和编码这三个步骤的缓存，不碰 OCR 和 LLM 缓存（LLM 重算要计费，而且结果有随机扰动）。漏提升规则版本靠协作约定里的检查时点防住，发现漏了就提升版本，或者用 `--refresh-cache` 重算。
- **B**：`--force` 一律绕过步骤缓存。漏提升版本时 `--force` 能纠正，但每次全量重建都要重算全部步骤，失去本版的主要收益。

**影响**：A 让"全量重建"变快；正确性取决于规则版本是否及时提升。

### 2. 编码结果要不要缓存

**事实**：七份配置中，不含表格的 chunk 文字大多相同，现在每份配置都要重新编码一遍。编码在全量重建中占多少时间还没有测，实施第 1 步会计时。

**选项**：
- **A（推荐）**：缓存。以"编码器身份 + 库版本 + chunk 文字"为键，存放向量，各配置共用。
- **B**：不缓存，只缓存解析和表格提取。

**影响**：A 的代价是多维护一个按 chunk 文字建键的库（`.rag/cache/embeddings.sqlite`）。第 1 步计时如果显示编码占比很小，我会回到这里提出改为 B。

## 目标

1. 一份文档只在影响它的输入（文件、设置、规则版本、库版本）变了的时候才重建。不受影响的文档、不受影响的步骤都不重做。
2. 影响它的输入只要有一项变了，这份文档就必须被判为过期，不能继续保留旧索引。
3. 全量重建时，各配置相同的步骤只算一次。
4. 现有 PDF 的 `chunks.json`（除 schema 版本外）与 13 种组合的指标不变。

## 改什么

### 1. 逐文档的构建指纹

- **废除整份索引的指纹。** manifest 里每份文档记录自己的构建设置和指纹。`status` 逐份比较，不再有整份索引的"配置已改变"状态，改为文档状态"设置已改变"，并写明是哪个步骤的设置变了。
- **一份文档的指纹只包含它实际经过的步骤**：
  - 公共步骤：分块、编码、BM25（配置了才计入）；
  - PDF 解析与表格提取：解析器、各表格提取器、选优与续表；
  - OCR：只对含扫描页的文档计入。按页面判定决定，页面判定只看文件本身，不用跑解析；
  - 表格三个环节（结构、写法、检索文本）：只对含表格的文档计入。按上次入库记录的表格数判断；表格数取决于解析和表格提取，这两步的设置已经在指纹里，所以这个判断是可靠的。
  - V4.2 起，Word 文档改走 Word 解析步骤，PDF 解析与表格提取不计入它的指纹。
- **`ingest` 的行为**：不加 `--force` 时，重建新增、已修改、设置已改变、不完整的文档，不再要求先 `--force`。`--force` 全量重建所有文档。
- **编码器身份变了**（向量维度可能不同）：向量库整体重建；这时所有文档本来也都是"设置已改变"。

### 2. 规则版本按步骤拆分

- 废除 `rag/config.py` 中统一的 `RULES_VERSION`。每个步骤在实现它的模块里定义自己的规则版本：
  - OCR：沿用现有的引擎身份，其中加入规则版本；
  - PDF 解析结果的转换与来源区域；
  - 表格选优与续表；
  - 表格三个环节；
  - 分块；
  - BM25 分析。
- 某个步骤的代码改变了它的输出，就提升这个步骤的版本，值写成发布它的版本号。
- LLM 的 `PROMPT_VERSION` 等现有规则项保持不变，仍归在表格环节。

### 3. 步骤结果缓存（`.rag/cache/`，各配置共用，不属于任何索引）

| 步骤 | 缓存的输出 | 键 |
|---|---|---|
| 解析 | 解析器的原始输出（Docling 解析时，含 Docling 自己的表格结果） | 解析用文件的哈希 + 解析器设置 + 解析规则版本 + 库版本 |
| 每个表格提取器 | 该提取器的表格候选 | 解析用文件的哈希 + 提取器设置 + 库版本 |
| 编码（拍板问题 2） | 每个 chunk 的向量 | 编码器身份 + 库版本 + chunk 文字 |

- 选优、续表、表格三个环节、分块计算成本低，不缓存，每次重算。LLM 调用照旧走 `.rag/llm-cache/`，OCR 照旧走 `.rag/ocr/`。
- 缓存只是加速，不改变判定：文档是否过期只由第 1 节的指纹决定。读到的缓存与重新计算的结果必须相同；验收时用"冷缓存全量重建"与"热缓存全量重建"的 `chunks.json` 逐字节比较来证明。
- 缓存不自动清理。`status` 显示缓存占用的空间。

### 4. 库版本进入指纹

每个步骤的身份里加入它直接调用的第三方库版本（解析：Docling 及其版面模型；表格提取：各工具的库；分块：计数用分词器的库与模型版本；编码：sentence-transformers 与 torch；BM25：词干化库）。只计入调用它的那个步骤，所以升级一个库只会让经过这一步的文档过期。版本号不论大小，有变化就算。

### 5. 可追溯

- `ingest` 的输出与入库记录逐份文档写明：每个步骤是读缓存还是重算，以及过期的原因（文件改变 / 哪一步的设置、规则或库版本改变 / 不完整）。
- 评估报告里的"构建设置"改为显示各步骤的设置与规则版本。

## 不改什么

- OCR 事实、LLM 缓存的格式与键不变。
- 查询、检索、评估的判定规则不变。
- 全量重建的"先全部处理完、再整体替换"的做法不变。

## 怎么验收

1. 八份配置（七份内置 + `plain_text`）冷缓存全量重建后，PDF 的 `chunks.json` 除 schema 版本外与 V4.1 逐字节相同；13 种组合的评估指标与 `reports/eval/2026-11-12_*` 相同。
2. 热缓存再全量重建一次，`chunks.json` 与冷缓存的结果逐字节相同。报告两次的耗时，以及 V4.1 的全量重建耗时（第 1 步计时）。
3. 重建完成后立即再运行 `ingest --all-configs`，没有任何文档被重建。
4. 单元测试：分别改动每一类设置、规则版本、库版本，被判为过期的文档恰好是经过该步骤的文档；缓存命中与重算的结果相同。
5. `pytest` 全部通过。
