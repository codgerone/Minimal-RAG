状态：**草稿，待审**　｜　分支：从 `main` 建 `index-rebuild`　｜　基线：V4.1（数据集 4.1.0）　｜　日期：2026-11-12

V4.2（Word）开工前先做这一版。V4.1.1 不加文档类型，数据集不变。

## 需要你拍板的问题

### 已定（2026-11-12）

| 问题 | 结论 |
|---|---|
| `--force` 要不要绕过步骤缓存 | 不绕过。另加 `ingest --refresh-cache`，只重算解析、表格提取、编码三个步骤的缓存，不碰 OCR 与 LLM 缓存；漏提升规则版本靠 `CLAUDE.md` 中的三个检查时点防住 |
| 编码结果要不要缓存 | 缓存，规则见第 3 节 |
| 缓存未命中的 chunk 怎么编码 | 逐条单独编码，使向量只由"编码器身份 + 库版本 + 文字"决定，缓存值与重算值逐位相同；第 1 步计时如果显示冷缓存慢得不可接受，再提出改回按批编码 |

### 3. 向量"相同"的判定标准

**事实**：
- 缓存未命中的 chunk 改为逐条单独编码（已定，见上表）。
- V4.1 的向量是按批编码的。同一段文字单独编码与和其他 chunk 一批编码相比，末几位不同（实验中最大绝对差 1.3×10⁻⁷），所以新旧向量不会逐位相同。
- 比较新旧向量时，要区分两种情况：一种是只因编码批次不同而产生的浮点差；另一种是编码的输入、模型或流程真的变了。

**推荐的标准**（三层都通过，才算与 V4.1 相同）：
1. **对应**：每个 chunk 编号在新旧索引中都有向量，向量维度相同，送入编码器的文字逐字节相同。
2. **数值**：对每个 chunk 计算新旧向量的差的范数 ‖Δv‖。门槛是"批次噪声上界"：所有不同的 chunk 文字分别按批大小 1、8、32，并与随机抽取的其他 chunk 组批编码，取同一文字各种编法两两之差范数的最大值。这个上界由一次独立的实验测出，不用 V4.1 的旧向量。任何一个 chunk 的 ‖Δv‖ 超过门槛，就不通过，并逐条列出这些 chunk。
3. **排名**：58 题的原问题在八份索引上做纯向量检索，比较新旧全量排名。查询向量和 chunk 向量都已归一化，所以一个 chunk 的分数变化不超过它的 ‖Δv‖；两个 chunk 只有在旧分数之差 ≤ 两者 ‖Δv‖ 之和时才可能互换名次。排名的每一处变化都必须满足这个条件，否则不通过。满足条件的名次互换逐条列出（预计没有），并报告它们是否改变了评估结果。混合检索的向量通道用的就是这份排名，所以这一层同时覆盖混合检索。

**影响**：
- 门槛由实验测出，不是人为选定的数。
- 第 2 层排除"输入或模型变了"。第 3 层把数值差落到检索结果上，并用一条可证明的不等式区分"近似并列的正常互换"和"异常变化"。
- 结果写入验收页，交你审核。

## 目标

1. 一份文档只在影响它的输入（文件、设置、规则版本、库版本）变了的时候才重建。不受影响的文档、不受影响的步骤都不重做。
2. 影响它的输入只要有一项变了，这份文档就必须被判为过期，不能继续保留旧索引。
3. 全量重建时，各配置相同的步骤只算一次。
4. 现有 PDF 的 `chunks.json`（除 schema 版本外）与 13 种组合的指标不变。

## 改什么

### 1. 逐文档的构建指纹

- **废除整份索引的指纹。** manifest 里每份文档记录自己的构建设置和指纹。`status` 逐份比较，不再有整份索引的"配置已改变"状态，改为文档状态"设置已改变"，并写明是哪个步骤的设置变了。
- **一份文档的指纹只包含它实际经过的步骤**：
  - 公共步骤：分块、编码、BM25（配置了才计入）；
  - PDF 解析与表格提取：解析器、各表格提取器、选优与续表；
  - OCR：只对含扫描页的文档计入。按页面判定决定，页面判定只看文件本身，不用跑解析；
  - 表格三个环节（结构、写法、检索文本）：只对含表格的文档计入。按上次入库记录的表格数判断；表格数取决于解析和表格提取，这两步的设置已经在指纹里，所以这个判断是可靠的。
  - V4.2 起，Word 文档改走 Word 解析步骤，PDF 解析与表格提取不计入它的指纹。
- **`ingest` 的行为**：不加 `--force` 时，重建新增、已修改、设置已改变、不完整的文档，不再要求先 `--force`。`--force` 全量重建所有文档。
- **编码器身份变了**（向量维度可能不同）：向量库整体重建；这时所有文档本来也都是"设置已改变"。

### 2. 规则版本按步骤拆分

- 废除 `rag/config.py` 中统一的 `RULES_VERSION`。每个步骤在实现它的模块里定义自己的规则版本：
  - OCR：沿用现有的引擎身份，其中加入规则版本；
  - PDF 解析结果的转换与来源区域；
  - 表格选优与续表；
  - 表格三个环节；
  - 分块；
  - BM25 分析。
- 某个步骤的代码改变了它的输出，就提升这个步骤的版本，值写成发布它的版本号。
- LLM 的 `PROMPT_VERSION` 等现有规则项保持不变，仍归在表格环节。

### 3. 步骤结果缓存（`.rag/cache/`，各配置共用，不属于任何索引）

| 步骤 | 缓存的输出 | 键 |
|---|---|---|
| 解析 | 解析器的原始输出（Docling 解析时，含 Docling 自己的表格结果） | 解析用文件的哈希 + 解析器设置 + 解析规则版本 + 库版本 |
| 每个表格提取器 | 该提取器的表格候选 | 解析用文件的哈希 + 提取器设置 + 库版本 |
| 编码 | 每个 chunk 的向量 | 编码器身份（模型、版本、前缀）+ 库版本 + 送入编码器的完整文字 |

- 选优、续表、表格三个环节、分块计算成本低，不缓存，每次重算。LLM 调用照旧走 `.rag/llm-cache/`，OCR 照旧走 `.rag/ocr/`。
- **编码缓存按文字查，不按 chunk 编号查。** chunk 编号（文档 + 序号）在各配置之间可能不同：表格 chunk 的数量不同，后面的编号就会错开。所以缓存里不存任何编号；入库时先按本配置分好块、编好号，再拿每个 chunk 的文字去查向量，最后按本配置的编号写入向量库。编号错开只影响写入的位置，不影响查到哪个向量。
- 未命中的 chunk 逐条单独编码（批大小 1），不与其他 chunk 组批。
- 键用完整文字的 SHA-256；缓存里同时存原文字，读出时与查询文字比较，不同就当作未命中并报错，排除哈希冲突和缓存损坏。
- 文字只要差一个字符（包括表格 chunk 因写法、引导句不同而不同），就是另一个键，重新编码；相同的文字不论来自哪个配置、哪份文档、第几块，都复用同一个向量。
- 缓存只是加速，不改变判定：文档是否过期只由第 1 节的指纹决定。读到的缓存与重新计算的结果必须相同；验收时用"冷缓存全量重建"与"热缓存全量重建"的 `chunks.json` 逐字节比较来证明。
- 缓存不自动清理。`status` 显示缓存占用的空间。

### 4. 库版本进入指纹

每个步骤的身份里加入它直接调用的第三方库版本（解析：Docling 及其版面模型；表格提取：各工具的库；分块：计数用分词器的库与模型版本；编码：sentence-transformers 与 torch；BM25：词干化库）。只计入调用它的那个步骤，所以升级一个库只会让经过这一步的文档过期。版本号不论大小，有变化就算。

### 5. 可追溯

- `ingest` 的输出与入库记录逐份文档写明：每个步骤是读缓存还是重算，以及过期的原因（文件改变 / 哪一步的设置、规则或库版本改变 / 不完整）。
- 评估报告里的"构建设置"改为显示各步骤的设置与规则版本。

## 不改什么

- OCR 事实、LLM 缓存的格式与键不变。
- 查询、检索、评估的判定规则不变。
- 全量重建的"先全部处理完、再整体替换"的做法不变。

## 怎么验收

1. 八份配置（七份内置 + `plain_text`）冷缓存全量重建后，与 V4.1 比较：PDF 的 `chunks.json` 除 schema 版本外逐字节相同；向量按拍板问题 3 的三层标准判定为相同；13 种组合的评估指标与 `reports/eval/2026-11-12_*` 相同。向量比较的结果写入验收页 `reports/experiments/v4.1.1-vectors/`。

3. 重建完成后立即再运行 `ingest --all-configs`，没有任何文档被重建。
4. 单元测试：分别改动每一类设置、规则版本、库版本，被判为过期的文档恰好是经过该步骤的文档；缓存命中与重算的结果相同。
5. `pytest` 全部通过。

### 第 2、3 步：实现中的调整（2026-11-12）

- OCR 结果目录的键包含 OCR 设置，设置中加入规则版本与库版本后键改变。4 份扫描件的 OCR 结果由 V4.1 的同一份代码、同一组库版本生成（库的安装日期早于 OCR 运行，代码差异只是新增常量），迁移到新键：目录改名，`ocr.json` 中记录的设置补上两个字段，识别结果不动。迁移前的目录备份在 scratchpad。

### 第 4 步：验收（2026-11-13）

- 第一次冷缓存全量重建发现：从缓存读回的表格提取报告，与重算的类型不同。Unstructured 适配器把页面像素高度以整数传入声明为 float 的字段，JSON 往返后变成 float。改为构造时转成 float（57797ed）：数值不变、chunk 不变，不提升规则版本。之后用最终代码重做验收。重建内存不足被系统停止过一次，改为每份配置单独一个进程。
- **冷缓存全量重建**（先清空 `.rag/cache/`，八份配置依次）：共 25.5 分钟（V4.1 约 110 分钟）。第一份 `structured` 14.4 分钟；其余六份内置配置解析、表格提取 9/9 命中，编码命中 118–136 / 139–157 个 chunk，每份约 1–1.2 分钟；`plain_text` 4.2 分钟（编码命中 5/888）。
- **热缓存全量重建**：共 6.1 分钟，所有步骤全部命中。与冷缓存的结果比较，八份索引的中间文件逐字节相同、向量逐位相同、BM25 与整表库内容相同。
- **立即再运行 `ingest`**（每份配置）：所有文档都是"无变化"，没有重建。
- **与 V4.1 比较中间结果**：`chunks.json` 八份配置全部逐字节相同。其余差异都已查明：
  - `pages.json`：只有 OCR 目录键（迁移所致）；
  - `parsed.json`（`structured_llm`、`structured_summary` 的扫描件）与 `tables.json`：LLM 调用记录中"是否读自缓存"的标记；
  - `tables.json`：189 处页面像素高度由整数写成数值相等的 float（上面的修正）。
- **向量**（三层标准，验收页 `reports/experiments/v4.1.1-vectors/`）：八份全部通过。
  - 对应：chunk 编号一一对应，维度 1024，文字不同 0 处。
  - 数值：批次噪声上界 6.62e-6（1170 段文字单独、8 条一批、32 条一批各编码一次）；新旧向量最大 ‖Δv‖ 七份内置配置 3.74e-6、`plain_text` 6.62e-6，超过上界 0 个。`plain_text` 的最大值与上界相等：批量编码可复现（8 条一批与 32 条一批 1053/1170 段逐位相同），该段文字 V4.1 的批量向量与本次组批的向量相同，两者与单独编码之差是同一个值。
  - 排名：58 题 × 8 份索引的纯向量全量排名，名次互换 4 处（都在 `plain_text`，第 248 名之后），旧分数差 ≤ 1e-7，都满足"旧分数差 ≤ 两者 ‖Δv‖ 之和"，违反 0 处。
- **单独编码的可复现性**：同一进程、不同进程在同一时段重新编码，结果彼此逐位相同；与冷缓存重建时存下的向量相比，884/1170 段逐位相同，其余差最大 7.0e-8（上界的 1%）。原因未查明（已用实验排除编码器设置不同、编码先后顺序两种）。步骤缓存使这种差不进入索引；`--refresh-cache` 重算时向量可能有这一量级的差。
- **评估**（`bash scripts/eval_tables.sh v4.1.1`，对比页 `reports/compare/v4.1.1/`）：13 种组合与 `reports/eval/2026-11-12_*` 逐题比较，指标、每题命中的 chunk 与名次、返回 token、表格证据全部相同；返回结果的相似度最多差 4.8e-7。
  - 数据集指纹不同，内容相同：指纹按 ground-truth 文件的原始字节计算，V4.1 合并到 `main` 时 git 按 `core.autocrlf` 重新检出了其中 5 个文件（换行改为 CRLF）；换回 LF 后算出的指纹与基线相同。这是原有问题，与本版无关。
- 规则版本检查（第 2 个时点）：验收用的索引入库后，入库侧代码只有 57797ed，不改变输出，不提升。
